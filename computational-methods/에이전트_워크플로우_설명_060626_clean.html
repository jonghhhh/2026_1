AI 에이전트에서 워크플로까지: 개념과 원리

대상: AI 에이전트를 처음 접하는 학부생·대학원생
목표: AI 에이전트의 작동 원리를 개념적으로 이해하고, 싱글 에이전트에서 멀티 에이전트, 워크플로우까지의 설계 사고방식을 갖춘다.

제1장. 챗봇은 왜 한계가 있는가?

1-1. 우리가 아는 챗봇

ChatGPT, Gemini 같은 대화형 AI를 떠올려 보자. 우리가 질문하면 답변한다. 이것을 그림으로 그리면 아래와 같이 매우 단순하다.

사용자: "서울 날씨 어때?"
   ↓
[  LLM  ]  ← 학습한 지식만으로 답변
   ↓
AI: "서울은 보통 이 시기에 25도 내외입니다."  ← 실시간 정보 아님!

이 방식에는 세 가지 근본적 한계가 있다.

한계 ①: 행동할 수 없다 LLM은 "말"만 할 수 있고, "행동"은 할 수 없다. 날씨 API를 호출하거나, 이메일을 보내거나, 파일을 저장하는 것은 불가능하다.

한계 ②: 기억하지 못한다 대화가 끝나면 이전 내용을 잊는다. "아까 내가 말한 거 기억해?"라고 물으면 못 한다.

한계 ③: 계획을 세우지 못한다 "내일 부산 출장 준비해줘"라고 하면, 기차표 예매 → 호텔 예약 → 일정표 작성이라는 여러 단계를 스스로 계획하고 실행하지 못한다. 그저 "이렇게 하시면 됩니다"라고 조언만 할 뿐이다.

1-2. 챗봇과 에이전트의 결정적 차이

챗봇 (Chatbot)AI 에이전트 (Agent)
하는 일질문에 답변목표를 달성하기 위해 스스로 판단·행동
도구 사용불가가능 (검색, 계산, API 호출 등)
기억대화 단위로 리셋단기·장기 메모리 보유
계획없음복잡한 작업을 하위 단계로 분해
반복1회 응답목표 달성까지 루프 반복
비유전화 안내 ARS유능한 비서

핵심 차이를 한 문장으로 요약하면 이렇다.

챗봇은 "대답하는 AI"이고, 에이전트는 "일하는 AI"이다.

제2장. AI 에이전트의 구조

2-1. 에이전트의 5가지 구성 요소

AI 에이전트는 사람의 비서와 놀라울 정도로 비슷한 구조를 가진다.

┌──────────────────────────────────────────────┐
│                 AI 에이전트                    │
│                                              │
│   🧠 두뇌 (LLM)         — 판단·추론 엔진     │
│   🔧 도구 (Tools)        — 외부 세계와 상호작용 │
│   📋 계획 (Planning)     — 작업 분해·순서 결정 │
│   💾 기억 (Memory)       — 과거 정보 저장·활용 │
│   👁️ 인식 (Perception)   — 입력·환경 이해     │
│                                              │
└──────────────────────────────────────────────┘

2-2. 🧠 두뇌 — LLM (Large Language Model)

에이전트의 두뇌는 LLM이다. GPT, Gemini, Claude 같은 대규모 언어 모델이 "다음에 무엇을 할지"를 판단한다.

사람으로 치면 회사의 신입사원 두뇌와 같다. 대학에서 많은 지식을 배웠지만(사전 학습), 실무에서는 도구(엑셀, 이메일)를 사용하고, 선배(사람)에게 확인받아야 제대로 일할 수 있다. LLM 혼자서는 "똑똑하지만 손발이 없는 상태"이고, 에이전트 시스템이 손발을 달아주는 것이다.

2-3. 🔧 도구 — Tools

도구는 에이전트가 외부 세계와 상호작용하는 수단이다.

도구 예시하는 일
웹 검색 (Web Search)실시간 정보 조회
계산기 (Calculator)수학 연산
코드 실행기 (Code Interpreter)Python 코드 실행
API 호출날씨, 주가, 뉴스 등 외부 데이터
파일 읽기/쓰기문서 생성, 데이터 저장
이메일 전송실제 메일 발송
데이터베이스 조회내부 데이터 검색

비유: 사무직 직원의 업무 도구다. 직원(LLM)이 "이 데이터가 필요하다"고 판단하면 엑셀(도구)을 열고, "보고서를 보내야 한다"고 판단하면 이메일(도구)을 쓴다. 도구가 없으면 판단만 하고 아무것도 실행할 수 없다.

2-4. 📋 계획 — Planning

복잡한 작업은 한 번에 끝나지 않는다. 에이전트는 큰 목표를 작은 단계로 분해한다.

예시: "다음 주 부산 출장을 준비해줘"

목표: 부산 출장 준비
  ├── 1단계: 출장 날짜 확인
  ├── 2단계: KTX 예매 (도구: 예매 API)
  ├── 3단계: 호텔 검색 및 예약 (도구: 호텔 API)
  ├── 4단계: 회의 일정 정리 (도구: 캘린더 API)
  └── 5단계: 출장 일정표 작성 (도구: 문서 생성)

사람도 마찬가지다. "출장 준비해"라는 지시를 받으면, 먼저 머릿속으로 "뭘 해야 하지?"를 정리한 뒤 순서대로 실행한다. 에이전트도 정확히 같은 사고 과정을 거친다.

2-5. 💾 기억 — Memory

기억은 두 종류로 나뉜다.

단기 기억 (Short-term / Working Memory) 현재 진행 중인 대화나 작업의 맥락을 기억한다. 회의 중에 화이트보드에 적는 내용과 같다. 회의가 끝나면 지운다.

장기 기억 (Long-term Memory) 이전 대화, 사용자 선호, 과거 작업 결과를 영구적으로 저장한다. 수첩에 적어 두고 나중에 다시 꺼내 보는 것과 같다.

[대화 1] "나는 채식주의자야"  →  장기 기억에 저장
         ...
[대화 50] "점심 추천해줘"    →  장기 기억 참조 → "채식 메뉴를 추천해 드릴게요"

2-6. 👁️ 인식 — Perception

에이전트는 다양한 형태의 입력을 이해할 수 있다.

텍스트: "이 기사를 요약해줘"
이미지: 차트 사진 → "이 그래프의 추세를 분석해줘"
파일:   PDF 업로드 → "이 논문의 핵심 내용은?"
데이터: CSV 파일 → "매출 트렌드를 분석해줘"

제3장. 에이전트는 어떻게 "생각"하는가?

3-1. Chain-of-Thought (CoT) — 단계별 사고

사람에게 "371 × 29는?"이라고 물으면, 대부분 암산이 어렵다. 하지만 종이에 풀어 쓰면 쉽게 답을 낸다. LLM도 마찬가지다.

일반 응답 (한 번에 답)

Q: 가게에 사과 23개가 있었다. 15개를 팔고, 새로 30개를 들여왔다. 몇 개?
A: 53개  ← 틀릴 수 있음

Chain-of-Thought (단계별 사고)

Q: 가게에 사과 23개가 있었다. 15개를 팔고, 새로 30개를 들여왔다. 몇 개?
A: 생각해 봅시다.
   1) 처음: 23개
   2) 15개를 팔면: 23 - 15 = 8개
   3) 30개를 들여오면: 8 + 30 = 38개
   답: 38개  ← 정확!

핵심은 중간 과정을 명시적으로 작성하는 것이다. LLM에게 "Let's think step by step"이라고 지시하면 정확도가 크게 향상된다.

3-2. 하지만 CoT만으로는 부족하다

Chain-of-Thought는 생각만 잘하는 것이다. 현실 문제를 풀려면 생각뿐 아니라 행동도 해야 한다.

질문: "삼성전자 오늘 주가가 얼마야?"

[CoT만 사용]
생각: 삼성전자는 대한민국 대표 기업이고, 최근 반도체 업황이...
답변: "약 30만원대일 것으로 추정됩니다."  ← 추측! 틀릴 수 있음

[CoT + 도구 사용]
생각: 실시간 주가가 필요하다. 검색 도구를 사용하자.
행동: search("삼성전자 오늘 주가")
관찰: "삼성전자 현재가 310,000원"
답변: "삼성전자의 현재 주가는 310,0300원입니다."  ← 정확!

이 문제를 해결하기 위해 등장한 것이 ReAct 패턴이다.

제4장. ReAct — 에이전트의 핵심 작동 원리

4-1. ReAct란?

ReAct는 Reasoning(추론) + Acting(행동)의 합성어로, 2022년 Princeton·Google 연구진이 발표한 에이전트 설계 패턴이다. 이 논문의 핵심 발견은 다음과 같다.

"LLM이 추론(생각)과 행동(도구 사용)을 번갈아 수행하면, 어느 한쪽만 하는 것보다 훨씬 정확하다."

4-2. ReAct 루프 — 생각 → 행동 → 관찰

ReAct 에이전트는 다음 세 단계를 반복(루프)한다.

┌─────────────────────────────────────────┐
│         ReAct 루프                       │
│                                          │
│  ① Thought (생각)                        │
│     "무엇을 해야 할까? 어떤 도구를 쓸까?"│
│              │                           │
│              ▼                           │
│  ② Action (행동)                         │
│     도구 호출: search("서울 날씨")        │
│              │                           │
│              ▼                           │
│  ③ Observation (관찰)                    │
│     결과 수신: "맑음, 25°C"              │
│              │                           │
│              ▼                           │
│  다시 ①로: "충분한 정보를 얻었나?"       │
│     ├── 아직 부족 → ①로 돌아감           │
│     └── 충분함 → 최종 답변 생성          │
└─────────────────────────────────────────┘

4-3. 구체적 사례로 이해하기

사례: "서울과 부산의 내일 날씨를 비교해줘"

[Thought 1] 두 도시의 날씨를 비교해야 한다. 먼저 서울 날씨를 검색하자.
[Action 1]  search_weather("서울")
[Observation 1] 서울: 맑음, 최고 27°C / 최저 18°C

[Thought 2] 서울 정보를 얻었다. 이제 부산 날씨를 검색하자.
[Action 2]  search_weather("부산")
[Observation 2] 부산: 흐림, 최고 24°C / 최저 20°C

[Thought 3] 두 도시 정보를 모두 얻었다. 비교 답변을 작성하자.
[Answer]    "서울은 맑고 27°C, 부산은 흐리고 24°C입니다.
             서울이 3도 높고, 부산은 우산을 챙기시는 게 좋겠습니다."

단 한 번의 LLM 호출이 아니라, 3번의 사고 + 2번의 도구 호출을 거쳐 정확한 답을 완성했다. 이것이 ReAct의 힘이다.

4-4. 왜 생각을 "소리 내어" 해야 하는가?

ReAct에서 가장 중요한 설계 원칙은 "생각을 명시적으로 출력한다"는 것이다.

방식내부 동작결과
생각 없이 행동바로 도구 호출 → 결과 받음 → 답변엉뚱한 도구를 호출하기 쉬움
생각한 뒤 행동이유를 적음 → 적합한 도구 선택 → 결과 → 답변정확하고 추적 가능

비유하면, 수학 시험에서 풀이 과정을 쓰는 것과 답만 쓰는 것의 차이다. 풀이 과정을 쓰면 중간에 실수를 발견하고 교정할 수 있다. LLM도 "생각"을 텍스트로 출력하면 논리적 오류를 줄일 수 있다.

4-5. ReAct vs 관련 개념 비교

개념설명한계
일반 LLM 응답질문 → 즉시 답변복잡한 문제에 취약, 환각(hallucination)
Chain-of-Thought단계별로 생각 → 답변생각만 함, 외부 정보 못 가져옴
도구 호출 (Tool Use)도구로 행동 → 결과 → 답변왜 그 도구를 쓰는지 추론 부족
ReAct생각 → 행동 → 관찰 → 반복추론과 행동의 결합, 가장 강력

제5장. 에이전트가 사용하는 도구의 원리

5-1. Function Calling (함수 호출)의 개념

LLM은 원래 텍스트만 생성한다. 그런데 어떻게 도구를 "호출"하는 것일까? 비밀은 Function Calling(함수 호출)이라는 기능에 있다.

원리는 의외로 간단하다.

[1단계: LLM에게 도구 목록을 알려준다]

"너는 아래 도구를 사용할 수 있어:
 - search_weather(city: str): 도시의 날씨를 검색
 - calculate(expression: str): 수학 계산을 실행"

[2단계: 사용자가 질문한다]

"서울 날씨가 어때?"

[3단계: LLM이 판단한다]

"이 질문에 답하려면 search_weather 도구를 사용해야 한다."

[4단계: LLM이 도구 호출을 "텍스트로" 출력한다]

{
  "tool": "search_weather",
  "arguments": {"city": "서울"}
}

[5단계: 시스템이 실제로 도구를 실행한다]

search_weather("서울") → "맑음, 25°C"

[6단계: 결과를 LLM에게 돌려준다]

"도구 결과: 맑음, 25°C"

[7단계: LLM이 최종 답변을 생성한다]

"서울의 현재 날씨는 맑음이고, 기온은 25°C입니다."

핵심을 짚으면, LLM이 직접 도구를 실행하는 것이 아니다. LLM은 "어떤 도구를 어떤 인자로 호출해야 하는지"를 JSON 형태로 출력하고, 실제 실행은 에이전트 프레임워크(LangGraph 등)가 담당한다. LLM은 지시서를 쓰는 역할, 프레임워크는 지시대로 실행하는 역할이다.

5-2. 도구 설명이 왜 중요한가?

LLM은 도구의 이름과 설명(description)을 보고 어떤 도구를 쓸지 결정한다. 따라서 도구 설명이 부실하면 LLM이 잘못된 도구를 선택한다.

# 나쁜 도구 설명
@tool
def func_a(x: str) -> str:
    """데이터를 처리합니다."""   # 뭘 처리한다는 건지 모호함
    ...

# 좋은 도구 설명
@tool
def search_weather(city: str) -> str:
    """주어진 도시의 현재 날씨(기온, 상태)를 검색합니다.
    Args:
        city: 날씨를 조회할 도시명 (예: '서울', '부산')
    Returns:
        날씨 상태와 기온 문자열"""
    ...

도구의 독스트링은 사람이 읽는 주석이 아니라, LLM이 읽는 사용 설명서다.

제6장. 에이전트 워크플로우 설계

6-1. 워크플로우란?

에이전트 워크플로우(Agent Workflow)는 에이전트가 목표를 달성하기 위해 거치는 작업 흐름을 구조화한 것이다. 아무 계획 없이 LLM에게 "알아서 해줘"라고 하면 비효율적이고 불안정하다. 마치 신입사원에게 "알아서 하세요"라고 하는 것과 같다. 업무 매뉴얼(워크플로우)이 있어야 일관되고 안정적인 결과를 얻는다.

6-2. 5가지 기본 워크플로우 패턴

패턴 ① 순차 파이프라인 (Sequential Pipeline)

[입력] → [A 단계] → [B 단계] → [C 단계] → [출력]

가장 단순한 패턴. 작업을 정해진 순서대로 처리한다.

사례: 뉴스 기사 자동 생성

[취재 데이터 입력] → [사실 확인] → [기사 초안 작성] → [문법 교정] → [최종 기사]

장점은 단순하고 예측 가능하다는 것, 단점은 유연성이 떨어진다는 것이다.

패턴 ② 조건부 분기 (Router / Conditional Branching)

              ┌──(조건A)──→ [처리A]
[입력] → [판단] ──(조건B)──→ [처리B]
              └──(조건C)──→ [처리C]

입력의 종류나 상태에 따라 다른 경로로 분기하는 패턴.

사례: 고객 문의 자동 분류

              ┌──(환불 문의)──→ [환불 처리 에이전트]
[고객 문의] → [분류기] ──(배송 문의)──→ [배송 추적 에이전트]
              └──(기술 문의)──→ [기술 지원 에이전트]

패턴 ③ ReAct 루프 (반복 판단)

[입력] → [LLM 판단] ←──┐
              │          │
         (도구 필요?)    │
          ├── 예 → [도구 실행] → [결과 관찰] ──┘
          └── 아니오 → [최종 답변]

앞서 배운 ReAct 패턴. 도구를 사용할 필요가 없어질 때까지 루프를 반복한다.

사례: 리서치 에이전트

"AI 에이전트 시장 규모 조사해줘"
→ 검색 → 결과 부족 → 다른 키워드로 재검색 → 충분 → 요약 답변

패턴 ④ 맵-리듀스 / Fan-out·Fan-in (병렬 처리)

              ┌→ [작업A] ──┐
[입력] → [분배] → [작업B] ──→ [통합] → [출력]
              └→ [작업C] ──┘

하나의 작업을 여러 개로 쪼개 동시에 처리한 뒤 결과를 합치는 패턴.

사례: 멀티 쿼리 RAG

"한국 경제 전망은?"
→ 동시에 3개 검색: ["GDP 성장률", "수출 동향", "고용 시장"]
→ 각 결과 수신
→ 종합 분석 보고서 작성

패턴 ⑤ 사람 개입 (Human-in-the-Loop)

[입력] → [AI 초안] → ⏸ [사람 검토/승인] → [실행] → [출력]

AI가 위험한 작업(이메일 발송, 결제 등)을 하기 전에 사람이 확인하는 패턴.

사례: 자동 이메일 발송

"거래처에 견적서 보내줘"
→ AI가 이메일 초안 작성
→ ⏸ "이대로 보낼까요?" (사람 확인)
→ 승인 시 발송 / 거절 시 수정

6-3. 패턴은 조합할 수 있다

현실의 에이전트는 이 패턴들을 레고 블록처럼 조합하여 사용한다.

[고객 문의] → [분류 (패턴②)]
    ├── 단순 문의 → [즉시 답변 (패턴①)]
    └── 복잡한 문의 → [리서치 (패턴③)]
                         → [답변 초안]
                         → ⏸ [상담원 확인 (패턴⑤)]
                         → [발송]

제7장. 멀티 에이전트 시스템

7-1. 왜 에이전트 하나로는 부족한가?

사람 세계를 생각해 보자. 작은 가게는 사장 혼자서 모든 일을 한다. 하지만 회사가 커지면 마케팅팀, 개발팀, 재무팀으로 나눠야 효율적이다. AI 에이전트도 마찬가지다.

상황싱글 에이전트멀티 에이전트
단순한 작업✅ 충분❌ 오히려 비효율
전문성이 필요한 작업❌ "만능"이 되어야 함✅ 전문가별 분업
긴 작업❌ 컨텍스트 한계✅ 역할별 독립 컨텍스트
검증이 필요한 작업❌ 자기 검증의 한계✅ 다른 에이전트가 검토

7-2. 멀티 에이전트 아키텍처 3가지

아키텍처 ① Supervisor (관리자-작업자)

                         ┌─→ [리서처] → 조사 결과
[사용자 요청] → [Supervisor] ─→ [코더]   → 코드 결과   → [Supervisor] → 최종 답변
                         └─→ [분석가] → 분석 결과

관리자(Supervisor)가 작업을 분배하고, 결과를 취합한다.

비유: 팀장이 팀원에게 업무를 나눠주고, 결과를 모아서 보고서를 쓰는 구조. 회사에서 가장 흔한 업무 방식이며, 멀티 에이전트에서도 가장 많이 쓰인다.

장점: 명확한 통제, 디버깅 용이 단점: 관리자가 병목(bottleneck)이 될 수 있음

사례: AI 뉴스룸

[편집장 에이전트 (Supervisor)]
  ├─→ [취재 에이전트]: 사실 조사, 인터뷰 자료 수집
  ├─→ [기사 작성 에이전트]: 초안 집필
  └─→ [교열 에이전트]: 맞춤법, 사실 확인, 최종 검수

아키텍처 ② 계층형 (Hierarchical)

              [총괄 관리자]
              ├── [팀장A]
              │    ├── [작업자1]
              │    └── [작업자2]
              └── [팀장B]
                   ├── [작업자3]
                   └── [작업자4]

Supervisor 패턴을 여러 층으로 쌓은 구조다. 큰 조직의 부서-팀-개인 체계와 동일하다. 복잡한 프로젝트에서 각 팀장이 자기 팀을 관리하고, 총괄 관리자가 팀장들을 조율한다.

사례: 대규모 보고서 작성

[총괄 PM]
  ├── [데이터팀 리더]
  │    ├── [데이터 수집 에이전트]
  │    └── [데이터 분석 에이전트]
  └── [문서팀 리더]
       ├── [본문 작성 에이전트]
       └── [시각화 에이전트]

아키텍처 ③ 스웜 (Swarm / Peer-to-Peer)

[에이전트A] ←→ [에이전트B]
     ↕              ↕
[에이전트C] ←→ [에이전트D]

중앙 관리자 없이 에이전트들이 서로 직접 소통하며 협력하는 구조. 벌떼(swarm)가 여왕벌 없이도 집단 지성으로 움직이는 것과 비슷하다.

장점: 유연함, 단일 실패 지점 없음 단점: 혼란 가능, 디버깅 어려움, 비용 예측 어려움

입문 단계에서는 Supervisor 패턴을 먼저 익히는 것을 권장한다. 가장 직관적이고, 실무에서도 가장 많이 사용되는 패턴이다.

7-3. 에이전트 간 소통 방식

멀티 에이전트에서 에이전트끼리 어떻게 정보를 주고받을까?

방식 ① 공유 상태 (Shared State) 모든 에이전트가 하나의 공유 메모장을 읽고 쓴다.

[공유 상태]
  messages: [사용자 질문, 리서처 결과, 코더 코드, ...]
  
리서처가 쓰면 → 코더가 읽음 → 코더가 쓰면 → Supervisor가 읽음

방식 ② 핸드오프 (Handoff) 에이전트A가 작업을 마치면 다음 에이전트에게 바통을 넘긴다.

[에이전트A] ──(결과 + 지시사항)──→ [에이전트B]

방식 ③ 메시지 패싱 (Message Passing) 에이전트가 서로에게 메시지를 보낸다.

에이전트A → 에이전트B: "번역 좀 해줘: 'Hello World'"
에이전트B → 에이전트A: "안녕하세요 세상"

7-4. 언제 멀티 에이전트를 써야 하는가?

멀티 에이전트는 강력하지만 비용이 많이 든다 (LLM 호출 횟수 증가). 아래 세 가지 조건 중 하나라도 해당하면 멀티 에이전트를 고려한다.

☑ 전문화: 서로 다른 전문 지식이 필요한 작업인가?
☑ 병렬성: 동시에 처리하면 시간을 크게 절약할 수 있는가?
☑ 검증:   한 에이전트의 결과를 다른 에이전트가 검토해야 하는가?

하나도 해당하지 않으면 싱글 에이전트가 더 효율적이다.

제8장. 에이전트를 더 똑똑하게 — 고급 패턴

8-1. 자기 성찰 (Reflection)

에이전트가 자신의 결과물을 스스로 평가하고 개선하는 패턴이다.

[초안 작성] → [자기 평가] → "부족한 부분이 있다"
                                    ↓
                            [수정된 버전 작성]
                                    ↓
                            [다시 자기 평가] → "이제 충분하다" → [최종 출력]

사례: 코드 작성 에이전트

1차: 코드 작성 → 실행 → 에러 발생
2차: 에러 원인 분석 → 수정 → 실행 → 성공!

사람도 글을 쓰면 퇴고(다시 읽고 고치기)를 한다. 에이전트의 자기 성찰도 같은 원리다.

8-2. 계획 후 실행 (Plan-and-Execute)

먼저 전체 계획을 세운 뒤, 각 단계를 순서대로 실행하는 패턴이다. ReAct가 "한 걸음씩 보며 걷기"라면, Plan-and-Execute는 "지도를 보고 경로를 정한 뒤 이동하기"이다.

[1단계: 계획 수립]
  "이 작업을 5단계로 나누겠다:
   ① 데이터 수집  ② 전처리  ③ 분석  ④ 시각화  ⑤ 보고서"

[2단계: 순차 실행]
  ① 데이터 수집 (실행 → 완료 ✅)
  ② 전처리 (실행 → 완료 ✅)
  ③ 분석 (실행 → 실패 ❌ → 계획 수정 → 재실행 → 완료 ✅)
  ④ 시각화 (실행 → 완료 ✅)
  ⑤ 보고서 (실행 → 완료 ✅)

ReAct보다 장기 작업에 적합하고, 중간에 실패해도 계획을 수정하여 계속 진행할 수 있다.

8-3. RAG — 지식 부족 해결

에이전트의 두뇌(LLM)는 학습 시점 이후의 정보나 내부 문서를 모른다. RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 외부 지식 저장소에서 관련 문서를 찾아 LLM에게 제공하는 기법이다.

사용자: "우리 회사 휴가 정책이 어떻게 돼?"

[에이전트의 RAG 프로세스]
  ① 질문을 벡터(숫자 표현)로 변환
  ② 사내 문서 DB에서 유사한 문서 검색
  ③ 검색된 문서: "연차는 입사 1년 후 15일 부여..."
  ④ LLM에게 문서와 질문을 함께 전달
  ⑤ LLM이 문서를 참고하여 답변 생성

RAG는 에이전트에게 "참고 자료를 찾아보는 능력"을 부여하는 것이다. 사람이 모르는 것을 찾아볼 때 도서관이나 구글을 이용하는 것과 같다.

제9장. 현실 세계의 에이전트 사례

9-1. 미디어·저널리즘

[편집장 에이전트]
  ├─ [취재 에이전트]: 웹 검색, 공공 데이터 수집
  ├─ [팩트체크 에이전트]: 주장-근거 교차 검증
  ├─ [기사 작성 에이전트]: 수집된 팩트를 기사로 구성
  └─ [교열 에이전트]: 맞춤법, 문체 통일, 최종 검수

9-2. 고객 서비스

[고객 문의 접수]
  → [의도 파악 에이전트]: "환불 요청인가? 상품 문의인가?"
  → [FAQ 검색 에이전트]: 기존 답변 DB에서 유사 사례 검색 (RAG)
  → [답변 생성 에이전트]: 맞춤형 답변 작성
  → ⏸ [상담원 검토] (복잡한 건만)
  → [답변 전송]

9-3. 데이터 분석

사용자: "지난 분기 매출 분석해줘"
  → [데이터 수집 에이전트]: DB에서 매출 데이터 추출
  → [분석 에이전트]: 트렌드 분석, 이상치 탐지 (Python 코드 실행)
  → [시각화 에이전트]: 차트 생성
  → [보고서 에이전트]: 분석 결과를 보고서 형태로 정리

9-4. 학술 연구

사용자: "최근 5년간 AI 에이전트 논문 동향을 분석해줘"
  → [논문 검색 에이전트]: 학술 DB에서 관련 논문 수집
  → [요약 에이전트]: 각 논문의 핵심 내용 요약
  → [트렌드 분석 에이전트]: 연도별 키워드 빈도, 연구 방법 변화 분석
  → [종합 보고서 에이전트]: 학술적 형식의 리뷰 보고서 작성

제10장. 에이전트 설계 시 고려사항

10-1. 할루시네이션 (환각) 문제

LLM은 가끔 없는 정보를 마치 있는 것처럼 생성한다. 이를 할루시네이션이라 한다.

사용자: "김철수 교수의 2024년 논문을 찾아줘"
에이전트: "김철수 교수의 '딥러닝과 미래' (2024)를 찾았습니다."
→ 실제로는 존재하지 않는 논문!

대응 방법: RAG를 통해 실제 문서를 검색하여 답변을 근거에 기반하게 만들고, 자기 성찰(Reflection)을 통해 결과를 검증한다.

10-2. 비용 관리

에이전트는 LLM을 여러 번 호출하므로 비용이 빠르게 증가한다.

싱글 챗봇:     1회 호출 = 1원
ReAct 에이전트: 5~10회 호출 = 5~10원
멀티 에이전트:  20~50회 호출 = 20~50원

대응 방법: 간단한 작업에는 작고 저렴한 모델(예: Gemini Flash Lite)을 사용하고, 복잡한 판단에만 큰 모델을 사용하는 모델 계층화 전략을 쓴다.

10-3. 안전성 — 되돌릴 수 없는 행동

에이전트가 이메일 발송, 파일 삭제, 결제 같은 되돌릴 수 없는 작업을 할 때는 반드시 사람의 확인(Human-in-the-Loop)을 거쳐야 한다.

[위험도 분류]
  낮음: 정보 검색, 요약, 분석 → 자동 실행 OK
  중간: 문서 생성, 데이터 수정 → 결과 확인 후 저장
  높음: 이메일 발송, 결제, 삭제 → 반드시 사람 승인

10-4. 디버깅과 추적

에이전트는 여러 단계를 거치므로, 어디서 문제가 생겼는지 파악하기 어렵다. 각 단계의 입력-출력을 기록(trace)하는 것이 중요하다.

[trace 예시]
  ┌ step1: user_input = "서울 날씨 알려줘"
  ├ step2: thought = "search_weather 도구를 사용하겠다"
  ├ step3: tool_call = search_weather("서울")
  ├ step4: tool_result = "맑음, 25°C"
  ├ step5: thought = "정보를 얻었으니 답변하겠다"
  └ step6: answer = "서울은 맑고 25°C입니다."

제11장. 개념에서 구현으로 — LangChain과 LangGraph

11-1. 프레임워크 선택 가이드

지금까지 배운 개념을 코드로 구현하려면 프레임워크가 필요하다.

[개념]                    →    [구현 프레임워크]
─────────────────────────────────────────────
LLM 호출, 도구 정의       →    LangChain
에이전트 워크플로우 설계   →    LangGraph
멀티 에이전트 오케스트레이션 →  LangGraph

LangChain은 LLM, 도구, 프롬프트를 다루는 부품(컴포넌트) 라이브러리이고, LangGraph는 이 부품들을 그래프 구조로 연결하여 워크플로우를 만드는 프레임워크이다.

비유하면, LangChain은 레고 블록 (각각의 부품)이고, LangGraph는 레고 조립 설명서 (부품을 어떤 순서로 어떻게 연결할지)이다.

11-2. 이 강의에서 배운 개념 → LangGraph 매핑

이론 개념LangGraph 구현
에이전트의 상태State (TypedDict)
작업 단계Node (노드, Python 함수)
작업 흐름 연결Edge (엣지)
조건부 분기Conditional Edge
도구 사용@tool 데코레이터 + ToolNode
ReAct 루프create_react_agent()
단기 기억MemorySaver (Checkpointer)
사람 개입interrupt() + Command(resume=)
SupervisorConditional Edge로 에이전트 라우팅

11-3. 빠른 맛보기 — 코드로 확인하는 개념

아래는 이 강의에서 배운 "ReAct 에이전트" 개념이 실제 코드에서 어떻게 구현되는지 보여주는 최소 예제다.

# ─── 환경 설정 ───
import os
from dotenv import load_dotenv
load_dotenv()
os.environ["GOOGLE_API_KEY"] = os.environ["GEMINI_API_KEY"]

# ─── ① 도구(Tool) 정의 — 에이전트의 손과 발 ───
from langchain_core.tools import tool

@tool
def search_weather(city: str) -> str:
    """주어진 도시의 현재 날씨를 검색합니다."""
    data = {"서울": "맑음, 25°C", "부산": "흐림, 22°C"}
    return data.get(city, f"{city}의 날씨 정보 없음")

@tool
def calculate(expression: str) -> str:
    """수학 계산식을 실행합니다. 예: '15 + 27'"""
    try:
        return f"결과: {eval(expression)}"
    except:
        return "계산 오류"

# ─── ② 두뇌(LLM) 준비 ───
from langchain_google_genai import ChatGoogleGenerativeAI
llm = ChatGoogleGenerativeAI(model="gemini-2.5-flash-lite")

# ─── ③ ReAct 에이전트 생성 — 단 한 줄! ───
from langgraph.prebuilt import create_react_agent
agent = create_react_agent(llm, [search_weather, calculate])

# ─── ④ 실행 ───
result = agent.invoke({
    "messages": [{"role": "user", "content": "서울 날씨 알려주고, 25+37 계산해줘"}]
})

for msg in result["messages"]:
    print(f"[{msg.type}] {msg.content}")

이 코드 안에 이론 강의의 핵심 개념이 모두 담겨 있다.

@tool 데코레이터        ←  5장: 도구 정의
ChatGoogleGenerativeAI  ←  2장: 에이전트의 두뇌(LLM)
create_react_agent      ←  4장: ReAct 루프 (생각→행동→관찰 반복)
messages                ←  8장: 대화 맥락 관리 (단기 기억)

11-4. 다음 단계: LangGraph 실습 강의로

이 이론 강의에서 배운 "왜"와 "무엇을"을 바탕으로, LangGraph 실습 강의에서는 "어떻게"를 다룬다.

[이론 강의 (이 문서)]          →    [LangGraph 실습 강의]
───────────────────────────────────────────────────────
ReAct 루프 개념               →    직접 그래프로 구현
조건부 분기 개념              →    add_conditional_edges
메모리 원리                   →    MemorySaver + thread_id
Human-in-the-Loop 원리        →    interrupt + Command
Supervisor 아키텍처           →    멀티 노드 그래프 구성
RAG 개념                     →    retrieve → generate 파이프라인
