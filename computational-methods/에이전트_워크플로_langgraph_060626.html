제1장. LangGraph — 에이전트 이론을 코드로 바꾸는 도구

1-1. 이론에서 코드로

이론 강의 11장에서 우리는 이렇게 정리했다.

"LangChain은 레고 블록(부품)이고, LangGraph는 레고 조립 설명서(흐름 설계)이다."

LangGraph는 이론 강의에서 배운 에이전트 워크플로우 패턴(순차, 분기, ReAct, 병렬, 사람 개입)을 그래프(Graph) 구조의 코드로 구현하게 해 주는 프레임워크다.

1-2. 핵심 비유: 지하철 노선도

이론 강의에서 워크플로우를 흐름도로 그렸다면, LangGraph는 그 흐름도를 실행 가능한 코드로 바꾸는 것이다. 비유하면 지하철 노선도와 같다.

제3장. 첫 번째 그래프 — "Hello LangGraph"

이론 연결: 이론 강의 2장(에이전트 구조)에서 배운 "상태"와 "작업 단계"를 코드로 만든다.

3-1. 전체 코드

# ============================================================
# 실습 3-1: 가장 단순한 LangGraph 그래프
# 이론 강의 2장의 "에이전트의 상태"와 "작업 단계"를 코드로 구현
# ============================================================

from langgraph.graph import StateGraph, START, END
from typing import TypedDict


# ── ① 상태(State) 정의 ──────────────────────────────────────
# 이론 강의 2장: 에이전트의 기억(Memory) = 여기서는 State
# TypedDict로 "이 그래프에서 어떤 데이터가 오갈 것인지" 선언한다
# 사람으로 치면 "릴레이 선수가 들고 뛰는 바통"의 내용물을 정의하는 것
class MyState(TypedDict):
    message: str  # 그래프 전체에서 공유할 메시지


# ── ② 노드(Node) 정의 ──────────────────────────────────────
# 이론 강의 6장: 워크플로우의 각 "작업 단계"가 곧 노드
# 규칙 1: 현재 상태(state)를 입력으로 받는다
# 규칙 2: 업데이트할 키-값 쌍을 딕셔너리로 반환한다
def greet(state: MyState) -> dict:
    name = state["message"]                       # 상태에서 이름을 꺼내고
    return {"message": f"안녕하세요, {name}님!"}   # 업데이트된 메시지를 반환


# ── ③ 그래프 조립 ───────────────────────────────────────────
# 이론 강의 6장: 워크플로우 = Node들을 Edge로 연결하는 것
graph = StateGraph(MyState)         # 상태 스키마로 그래프 생성
graph.add_node("greet", greet)      # 노드 등록 (이름, 함수)
graph.add_edge(START, "greet")      # START → greet 연결
graph.add_edge("greet", END)        # greet → END 연결


# ── ④ 컴파일 & 실행 ────────────────────────────────────────
# compile()은 그래프를 "실행 가능한 형태"로 변환한다 (건축 설계도 → 실제 건물)
app = graph.compile()

# invoke()로 초기 상태를 넣고 실행
result = app.invoke({"message": "민수"})
print(result["message"])
# 출력: 안녕하세요, 민수님!

제4장. 순차 파이프라인 — 여러 단계를 연결

이론 연결: 이론 강의 6장 워크플로우 패턴① "Sequential Workflow (순차)" (A → B → C)

4-1. 예제: 기사 데이터 처리 파이프라인

미디어 분야 사례로, 뉴스 기사 텍스트를 단계별로 처리하는 파이프라인을 만들자.

# ============================================================
# 실습 4-1: 순차 파이프라인 — 뉴스 기사 처리
# 이론 강의 6장 패턴①: [입력] → [A] → [B] → [C] → [출력]
# ============================================================

from langgraph.graph import StateGraph, START, END
from typing import TypedDict


class ArticleState(TypedDict):
    raw_text: str       # 원본 텍스트
    cleaned: str        # 정제된 텍스트
    word_count: int     # 단어 수
    summary: str        # 최종 요약


# ── 노드 1: 텍스트 정제 (공백·특수문자 제거) ────────────────
def clean_text(state: ArticleState) -> dict:
    text = state["raw_text"]
    # 앞뒤 공백 제거, 연속 공백을 하나로
    cleaned = " ".join(text.split())
    print(f"  [clean_text] 정제 완료: {len(text)}자 → {len(cleaned)}자")
    return {"cleaned": cleaned}


# ── 노드 2: 단어 수 세기 ────────────────────────────────────
def count_words(state: ArticleState) -> dict:
    count = len(state["cleaned"].split())
    print(f"  [count_words] 단어 수: {count}개")
    return {"word_count": count}


# ── 노드 3: 요약 생성 ──────────────────────────────────────
def make_summary(state: ArticleState) -> dict:
    text = state["cleaned"]
    count = state["word_count"]
    # 간단한 요약: 첫 50자 발췌
    excerpt = text[:50] + "..." if len(text) > 50 else text
    summary = f"[{count}단어] {excerpt}"
    print(f"  [make_summary] 요약 생성 완료")
    return {"summary": summary}


# ── 그래프 조립: 3단계 공식 적용 ────────────────────────────
graph = StateGraph(ArticleState)

# ① 노드 등록
graph.add_node("clean_text", clean_text)
graph.add_node("count_words", count_words)
graph.add_node("make_summary", make_summary)

# ② 순차 연결: START → clean → count → summary → END
graph.add_edge(START, "clean_text")
graph.add_edge("clean_text", "count_words")
graph.add_edge("count_words", "make_summary")
graph.add_edge("make_summary", END)

# ③ 컴파일 & 실행
app = graph.compile()

result = app.invoke({
    "raw_text": "  LangGraph는   AI 에이전트를   위한   강력한  프레임워크이다.  ",
    "cleaned": "",
    "word_count": 0,
    "summary": ""
})

print(f"\n최종 결과: {result['summary']}")

핵심 포인트: clean_text가 업데이트한 cleaned를 → count_words가 읽고, count_words가 업데이트한 word_count를 → make_summary가 읽는다. 상태가 바통처럼 노드를 따라 전달되는 것이다.

제5장. 조건부 분기 — 상황에 따라 다른 경로

이론 연결: 이론 강의 6장 워크플로우 패턴③ "Routing Workflow (분기)"

5-1. 개념 복습

이론 강의에서 고객 문의 자동 분류를 예로 들었다.

              ┌──(환불 문의)──→ [환불 처리 에이전트]
[고객 문의] → [분류기] ──(배송 문의)──→ [배송 추적 에이전트]
              └──(기술 문의)──→ [기술 지원 에이전트]

이것을 LangGraph 코드로 만들면 add_conditional_edges가 된다.

5-2. 예제: 감정 분석 후 분기 응답

# ============================================================
# 실습 5-2: 조건부 분기 — 감정 분석 라우터
# 이론 강의 6장 패턴②: 입력 → [판단] → 조건에 따라 다른 경로
# ============================================================

from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Literal


class MoodState(TypedDict):
    user_input: str   # 사용자 입력 텍스트
    mood: str         # 분석된 감정 (positive / negative)
    reply: str        # 생성된 응답


# ── 노드 1: 감정 분석 (키워드 기반 간단 버전) ────────────────
# 이론 강의 6장: "입력의 종류나 상태에 따라 다른 경로로 분기"
def analyze_mood(state: MoodState) -> dict:
    text = state["user_input"]
    positive_words = ["좋아", "행복", "감사", "기쁘", "최고", "사랑", "재밌"]
    # 긍정 키워드가 하나라도 포함되면 "positive"
    if any(word in text for word in positive_words):
        return {"mood": "positive"}
    else:
        return {"mood": "negative"}


# ── 노드 2a: 긍정 응답 ─────────────────────────────────────
def positive_reply(state: MoodState) -> dict:
    return {"reply": f"좋은 소식이네요! '{state['user_input']}'라니 기쁩니다 😊"}


# ── 노드 2b: 부정 응답 ─────────────────────────────────────
def negative_reply(state: MoodState) -> dict:
    return {"reply": f"힘든 일이 있으셨군요. 이야기해 주시면 도움이 될 거예요."}


# ── 라우팅 함수: 어느 노드로 갈지 결정 ──────────────────────
# 이 함수의 반환값이 "다음 노드의 이름"이 된다
# Literal 타입 힌트로 가능한 반환값을 명시하면 LangGraph가 검증해 준다
def route_by_mood(state: MoodState) -> Literal["positive_reply", "negative_reply"]:
    if state["mood"] == "positive":
        return "positive_reply"    # → positive_reply 노드로 이동
    else:
        return "negative_reply"    # → negative_reply 노드로 이동


# ── 그래프 조립 ─────────────────────────────────────────────
graph = StateGraph(MoodState)
graph.add_node("analyze_mood", analyze_mood)
graph.add_node("positive_reply", positive_reply)
graph.add_node("negative_reply", negative_reply)

graph.add_edge(START, "analyze_mood")

# ★ 핵심: add_conditional_edges — 조건부 분기!
# analyze_mood 실행 후 → route_by_mood 함수가 다음 경로를 결정
graph.add_conditional_edges("analyze_mood", route_by_mood)

graph.add_edge("positive_reply", END)
graph.add_edge("negative_reply", END)

app = graph.compile()

제6장. LLM 연결 — AI 챗봇 만들기

이론 연결: 이론 강의 2장(두뇌 = LLM)을 실제로 연결한다. 챗봇은 에이전트의 출발점이다.

6-1. MessagesState — 채팅 전용 상태

LangGraph는 채팅 메시지를 다루기 위한 편리한 내장 상태를 제공한다.

from langgraph.graph import MessagesState

# MessagesState는 내부적으로 이런 구조:
# class MessagesState(TypedDict):
#     messages: Annotated[list, add_messages]
#
# add_messages의 역할: 새 메시지를 기존 리스트에 "추가"(덮어쓰기가 아닌 누적)

6-2. 기본 챗봇

# ============================================================
# 실습 6-2: Gemini 연결 기본 챗봇
# 이론 강의 2장: 에이전트의 두뇌(LLM)를 그래프에 연결
# 이론 강의 1장: 아직은 "챗봇" 수준 — 도구도 없고 기억도 없다
# ============================================================

from langgraph.graph import StateGraph, MessagesState, START, END
from langchain_google_genai import ChatGoogleGenerativeAI

# ── LLM 초기화 ─────────────────────────────────────────────
# 이론 강의 2장: "에이전트의 두뇌는 LLM이다"
# temperature: 0에 가까울수록 일관된 답변, 1에 가까울수록 창의적 답변
llm = ChatGoogleGenerativeAI(model="gemini-2.5-flash-lite", temperature=0.7)


# ── 챗봇 노드 ──────────────────────────────────────────────
# state["messages"]에 든 전체 대화 내역을 LLM에게 보내고,
# AI 응답을 messages 리스트에 추가하여 반환
def chatbot(state: MessagesState) -> dict:
    response = llm.invoke(state["messages"])  # LLM 호출
    return {"messages": [response]}           # 응답을 리스트에 추가


# ── 그래프 ──────────────────────────────────────────────────
graph = StateGraph(MessagesState)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)

app = graph.compile()


# ── 실행 ────────────────────────────────────────────────────
result = app.invoke({
    "messages": [{"role": "user", "content": "LangGraph가 뭐야? 한 줄로 설명해줘."}]
})

# result는 아래와 같은 구조로 반환된다:
# {
#     'messages': [
#         HumanMessage(content='LangGraph가 뭐야? 한 줄로 설명해줘.'),
#         AIMessage(content='LangGraph는 복잡한 워크플로우를 그래프 형태로 정의하고
#                            실행할 수 있게 해주는 라이브러리입니다.')
#     ]
# }
# → messages 리스트에 사용자 메시지(HumanMessage)와 AI 응답(AIMessage)이 누적된다.

# 마지막 메시지 = AI 응답

제7장. 도구(Tool)와 ReAct 에이전트

이론 연결: 이론 강의 4장(ReAct 루프)과 5장(Function Calling 원리)을 코드로 구현한다. 이 장이 "챗봇 → 에이전트"로 바뀌는 결정적 순간이다.

7-1. 복습: 이론에서 배운 ReAct

이론 강의 4장의 ReAct 루프:
  ① Thought (생각)  → "어떤 도구를 쓸까?"
  ② Action (행동)   → 도구 호출
  ③ Observation (관찰) → 결과 수신
  → 충분하면 답변, 부족하면 ①로 돌아감

이제 이것을 LangGraph로 구현한다.

7-2. 도구 정의하기

# ============================================================
# 실습 7-2: 도구(Tool) 정의
# 이론 강의 5장: "LLM이 직접 도구를 실행하는 것이 아니다"
# → LLM은 "어떤 도구를 쓸지" JSON으로 지시하고,
#   프레임워크(LangGraph)가 실제 실행을 담당한다
# ============================================================

from langchain_core.tools import tool

# ── 도구 1: 날씨 검색 ──────────────────────────────────────
# @tool 데코레이터: 일반 함수를 "LLM이 호출 가능한 도구"로 변환
# 독스트링("""...""")이 매우 중요 — LLM이 이것을 읽고 도구 사용 여부를 판단
# 이론 강의 5장: "도구의 독스트링은 LLM이 읽는 사용 설명서"
@tool
def search_weather(city: str) -> str:
    """주어진 도시의 현재 날씨(기온, 상태)를 검색합니다.
    Args:
        city: 날씨를 조회할 도시명 (예: '서울', '부산', '제주')
    Returns:
        날씨 상태와 기온 문자열
    """
    # 실제로는 날씨 API를 호출하겠지만, 여기서는 예시 데이터 사용
    weather_data = {
        "서울": "맑음, 25°C, 습도 45%",
        "부산": "흐림, 22°C, 습도 70%",
        "제주": "비, 20°C, 습도 85%",
        "대전": "맑음, 26°C, 습도 40%",
    }
    return weather_data.get(city, f"{city}의 날씨 정보를 찾을 수 없습니다.")


# ── 도구 2: 계산기 ─────────────────────────────────────────
@tool
def calculate(expression: str) -> str:
    """수학 계산식을 실행합니다.
    Args:
        expression: 파이썬 문법의 수학식 (예: '2 + 3 * 4', '100 / 7')
    Returns:
        계산 결과 문자열
    """
    try:
        result = eval(expression)
        return f"계산 결과: {result}"
    except Exception as e:
        return f"계산 오류: {e}"


# ── 도구 3: 뉴스 검색 (가상) ────────────────────────────────
@tool
def search_news(topic: str) -> str:
    """주어진 주제에 대한 최신 뉴스 헤드라인을 검색합니다.
    Args:
        topic: 검색할 뉴스 주제 (예: 'AI', '경제', '스포츠')
    Returns:
        관련 뉴스 헤드라인 3개
    """
    news_db = {
        "AI": "1) AI 에이전트 시장 525억 달러 전망\n2) 구글, 새 Gemini 모델 발표\n3) 국내 기업 AI 도입률 57% 돌파",
        "경제": "1) 한국은행 기준금리 동결\n2) 코스피 3000선 돌파\n3) 수출 6개월 연속 증가",
        "스포츠": "1) 손흥민 시즌 20호골\n2) MLB 류현진 복귀전 승리\n3) 파리 올림픽 메달 순위 발표",
    }
    return news_db.get(topic, f"'{topic}' 관련 뉴스를 찾을 수 없습니다.")

print("도구 3개 정의 완료: search_weather, calculate, search_news")

7-3. 방법 A: create_agent (LangChain 1.x 표준)

# ============================================================
# 실습 7-3: ReAct 에이전트 — 한 줄 생성
# 이론 강의 4장의 ReAct 루프가 내부적으로 자동 구성된다
# ============================================================

from langchain.agents import create_agent
from langchain_google_genai import ChatGoogleGenerativeAI

# 두뇌(LLM) 준비
llm = ChatGoogleGenerativeAI(model="gemini-2.5-flash-lite")

# 도구 목록 — 에이전트가 사용할 수 있는 도구들
tools = [search_weather, calculate, search_news]

# ★ 한 줄로 ReAct 에이전트 생성!
# 내부적으로 이론 강의 4장의 Thought → Action → Observation 루프가 구성됨
agent = create_agent(llm, tools)


# ── 테스트 1: 도구 하나 사용 ────────────────────────────────
result = agent.invoke({
    "messages": [{"role": "user", "content": "제주도 날씨가 어때?"}]
})
# 전체 메시지 흐름 출력 — ReAct 루프를 직접 확인할 수 있다
for msg in result["messages"]:
    role = getattr(msg, 'type', 'unknown')
    content = getattr(msg, 'content', '')
    print(f"[{role}] {content[:200]}")
print()


# ── 테스트 2: 도구 두 개 순차 사용 ──────────────────────────
# 이론 강의 4장 사례: "서울과 부산 날씨를 비교해줘"와 같은 구조
result = agent.invoke({
    "messages": [{"role": "user", "content": "서울이랑 부산 날씨 비교해주고, 온도 차이도 계산해줘"}]
})
print("최종 답변:", result["messages"][-1].content)
print()


# ── 테스트 3: 도구 선택 판단 ────────────────────────────────
# LLM이 "어떤 도구를 쓸지" 스스로 판단하는 것을 확인
result = agent.invoke({
    "messages": [{"role": "user", "content": "AI 관련 최신 뉴스 알려줘"}]
})

7-4. 방법 B: 직접 그래프로 구현 (원리 이해용)

create_agent가 내부에서 무엇을 하는지 직접 만들어 보면 ReAct 루프가 명확히 이해된다.

# ============================================================
# 실습 7-4: ReAct 에이전트 — 직접 그래프 구현
# create_agent의 내부 구조를 직접 만들어 본다
# 이론 강의 4장의 ReAct 루프를 그래프의 노드·엣지로 표현
# ============================================================

from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.prebuilt import ToolNode
from langchain_google_genai import ChatGoogleGenerativeAI

# ── LLM에 도구 목록 알려주기 ────────────────────────────────
# bind_tools()는 LLM에게 "너는 이 도구들을 사용할 수 있어"라고 알려주는 것
# 이론 강의 5장의 [1단계]: "LLM에게 도구 목록을 알려준다"
llm = ChatGoogleGenerativeAI(model="gemini-2.5-flash-lite")
tools = [search_weather, calculate, search_news]
llm_with_tools = llm.bind_tools(tools)


# ── 노드 1: LLM 사고 ───────────────────────────────────────
# 이론 강의 4장 ① Thought: "무엇을 해야 할까? 어떤 도구를 쓸까?"
# LLM이 사고하고, 도구를 쓸지 말지를 결정한다
def call_llm(state: MessagesState) -> dict:
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}


# ── 노드 2: 도구 실행 ──────────────────────────────────────
# 이론 강의 4장 ② Action: 도구 호출
# 이론 강의 5장 [5단계]: "시스템이 실제로 도구를 실행한다"
# ToolNode는 LangGraph가 제공하는 내장 노드 — 도구 실행을 자동 처리
tool_node = ToolNode(tools)


# ── 라우팅: 도구 호출이 필요한지 판단 ───────────────────────
# 이론 강의 4장: "충분한 정보를 얻었나? → 아직 부족 → ①로 돌아감"
# LLM 응답에 tool_calls가 있으면 → 도구 실행으로
# tool_calls가 없으면 → 답변 완성, 종료
def should_use_tool(state: MessagesState):   # LLM의 판단 결과를 읽는 것이지, 스스로 판단하는 것이 아님.
    last_msg = state["messages"][-1]
    # tool_calls 속성이 있고, 비어있지 않으면 → 도구 사용
    if hasattr(last_msg, "tool_calls") and last_msg.tool_calls:
        return "tools"
    # 도구 호출 없음 → 최종 답변 완성 → 종료
    return END


# ── 그래프 조립 ─────────────────────────────────────────────
# 이론 강의 6장 패턴③ ReAct 루프:
# [LLM 판단] ←──(반복)──→ [도구 실행]
#     │
#     └──(완료)──→ [END]
graph = StateGraph(MessagesState)
graph.add_node("llm", call_llm)
graph.add_node("tools", tool_node)

graph.add_edge(START, "llm")                         # 시작 → LLM
graph.add_conditional_edges("llm", should_use_tool)   # LLM → 도구? or 종료?
graph.add_edge("tools", "llm")                        # 도구 결과 → 다시 LLM (루프!)

app = graph.compile()

# 시각화 — ReAct 루프 구조 확인
print(app.get_graph().draw_ascii())
이 그래프의 구조:

[START] → [llm] ──(도구 필요?)──→ [tools] ──→ [llm] (반복)
              │
              └──(도구 불필요)──→ [END]

↑ 이것이 바로 이론 강의 4장의 ReAct 루프를 코드로 옮긴 것이다!

제8장. 대화 기억 — 메모리(Memory) 구현

이론 연결: 이론 강의 2장(에이전트의 기억)에서 배운 "단기 기억"을 구현한다. 이론 강의 1장의 한계②("기억하지 못한다")를 해결하는 장이다.

8-1. 문제 확인: 기억 없는 챗봇

# 메모리 없이 두 번 호출하면?
result1 = app.invoke({"messages": [{"role": "user", "content": "내 이름은 민수야"}]})
result2 = app.invoke({"messages": [{"role": "user", "content": "내 이름이 뭐였지?"}]})
# → "죄송합니다, 이름을 알려주시지 않으셨는데요." (기억 못함!)
# invoke()를 할 때마다 상태가 초기화되기 때문!

8-2. 해결: Checkpointer (단기 기억)

# ============================================================
# 실습 8-2: 단기 기억 챗봇
# 이론 강의 2장: "단기 기억 = 회의 중 화이트보드"
# 같은 thread_id로 대화하면 이전 내용을 기억한다  

# LangGraph에는 사용자 정보를 장기간 저장하는 Store(Long-Term Memory) 기능도 있다. 그러나 기사, 논문, 설문 데이터와 같은 분석 자료는 일반적으로 Vector DB나 데이터베이스에 저장하므로, 여기에서는 Checkpointer만 다룬다  
# ============================================================

from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import MemorySaver
from langchain_google_genai import ChatGoogleGenerativeAI

llm = ChatGoogleGenerativeAI(model="gemini-2.5-flash-lite")


def chatbot(state: MessagesState) -> dict:
    return {"messages": [llm.invoke(state["messages"])]}


graph = StateGraph(MessagesState)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)

# ★ 핵심: MemorySaver를 체크포인터로 지정
# 이론 강의 2장: 단기 기억 장치를 에이전트에 장착하는 것
memory = MemorySaver()
app = graph.compile(checkpointer=memory)


# ── thread_id: 대화방 개념 ──────────────────────────────────
# 같은 thread_id = 같은 채팅방 → 이전 대화 기억
# 다른 thread_id = 다른 채팅방 → 서로 독립
# 카카오톡 채팅방과 같은 개념이다
config = {"configurable": {"thread_id": "student-minsu"}}

# 대화 1
result1 = app.invoke(
    {"messages": [{"role": "user", "content": "안녕! 내 이름은 민수야."}]},
    config=config
)
print("AI:", result1["messages"][-1].content)

# 대화 2 — 같은 thread_id이므로 이전 대화를 기억!
result2 = app.invoke(
    {"messages": [{"role": "user", "content": "내 이름이 뭐라고 했지?"}]},
    config=config
)
print("AI:", result2["messages"][-1].content)
# → "민수님이라고 하셨죠!" (기억함!)

# 대화 3 — 다른 thread_id는 독립된 대화
config_other = {"configurable": {"thread_id": "student-jiyoung"}}
result3 = app.invoke(
    {"messages": [{"role": "user", "content": "내 이름 아는?"}]},
    config=config_other
)
print("AI:", result3["messages"][-1].content)
# → "아직 이름을 알려주시지 않으셨는데요." (다른 채팅방이니까!)

8-3. 시스템 메시지로 성격 부여

# ============================================================
# 실습 8-3: 성격 있는 챗봇 (시스템 메시지 + 메모리)
# ============================================================

from langchain_core.messages import SystemMessage

config = {"configurable": {"thread_id": "korean-teacher"}}

# 첫 대화에 시스템 메시지를 포함하면 챗봇의 "성격"이 설정된다
result = app.invoke(
    {"messages": [
        # 시스템 메시지: 챗봇의 역할을 지정

제9장. 사람의 개입 — Human-in-the-Loop

이론 연결: 이론 강의 6장 패턴⑤ "사람 개입"과 10장(안전성)을 구현한다.
이론 강의 10장에서 배웠다: *"되돌릴 수 없는 작업(이메일, 결제, 삭제)은 반드시 사람 승인을 거쳐야 한다."*

9-1. interrupt로 일시정지

# ============================================================
# 실습 9-1: Human-in-the-Loop — 이메일 발송 전 사람 확인
# 이론 강의 10장: "높은 위험도 작업은 반드시 사람 승인"
# ============================================================

from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import interrupt, Command


# ── 노드 1: AI가 이메일 초안 작성 ──────────────────────────
def draft_email(state: MessagesState) -> dict:
    draft = "김팀장님, 다음 주 회의 일정을 변경하고 싶습니다. 화요일 2시는 어떠신가요?"
    return {"messages": [{"role": "ai", "content": f"이메일 초안:\n\n{draft}"}]}


# ── 노드 2: 사람의 승인을 기다린다 ─────────────────────────
# interrupt()가 호출되면 그래프 실행이 일시정지(⏸)된다
# 사람이 Command(resume=...)로 응답할 때까지 대기
def human_review(state: MessagesState) -> dict:
    # 이 시점에서 실행이 멈추고, 사람의 입력을 기다린다
    decision = interrupt("이메일을 보낼까요? (yes/no)")

    if decision == "yes":
        return {"messages": [{"role": "ai", "content": "✅ 이메일을 전송했습니다!"}]}
    else:
        return {"messages": [{"role": "ai", "content": "❌ 전송을 취소했습니다."}]}


# ── 그래프 조립 ─────────────────────────────────────────────
graph = StateGraph(MessagesState)
graph.add_node("draft", draft_email)
graph.add_node("review", human_review)
graph.add_edge(START, "draft")
graph.add_edge("draft", "review")
graph.add_edge("review", END)

# interrupt를 쓰려면 반드시 checkpointer가 필요
app = graph.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "email-001"}}

# ── 1단계: 실행 → review 노드에서 멈춤 ─────────────────────
print("--- 1단계: 그래프 실행 ---")
result = app.invoke(
    {"messages": [{"role": "user", "content": "팀장님께 회의 변경 이메일 보내줘"}]},
    config=config
)
# 이 시점에서 draft는 실행 완료, review는 interrupt에서 일시정지 상태
for msg in result["messages"]:
    print(f"  {msg.content if hasattr(msg, 'content') else msg['content']}")

# ── 2단계: 사람이 승인 후 재개 ──────────────────────────────
print("\n--- 2단계: 사람 승인 후 재개 ---")
result = app.invoke(
    Command(resume="yes"),  # 사람의 결정
    config=config
)
print(f"  {result['messages'][-1].content}")

9-2. 실행 흐름 요약

[START] → [draft] → [review] ──── ⏸ 일시정지
                                        │
                                   사람: "yes" (Command)
                                        │
                                        ▼
                                "이메일 전송!" → [END]

제11장. RAG — 검색 증강 생성

이론 연결: 이론 강의 8장(RAG 개념)을 LangGraph 그래프로 구현한다.
이론 강의에서 배웠다: *"RAG는 에이전트에게 '참고 자료를 찾아보는 능력'을 부여하는 것"*

11-1. 이론 복습 → 코드 구조

이론 강의 8장의 RAG 프로세스:
  ① 질문 입력
  ② 문서 DB에서 검색 (Retrieval)
  ③ 검색된 문서를 LLM에게 전달
  ④ LLM이 문서를 참고하여 답변 생성 (Generation)

LangGraph 그래프로 표현하면:
  [START] → [retrieve] → [generate] → [END]

11-2. 구현

# ============================================================
# 실습 11-2: 간단한 RAG 파이프라인
# 이론 강의 8장: "외부 문서를 검색 → LLM에게 참고 자료로 제공 → 답변"
# 이론 강의 10장: 할루시네이션 대응 — 근거 기반 답변 생성
# ============================================================

from langgraph.graph import StateGraph, START, END
from typing import TypedDict
from langchain_google_genai import ChatGoogleGenerativeAI

llm = ChatGoogleGenerativeAI(model="gemini-2.5-flash-lite")


class RAGState(TypedDict):
    question: str          # 사용자 질문
    documents: list[str]   # 검색된 문서 목록
    answer: str            # 최종 답변


# ── 가상 문서 데이터베이스 ──────────────────────────────────
# 실무에서는 ChromaDB, Pinecone 같은 벡터 DB를 사용
KNOWLEDGE_BASE = [
    "LangGraph는 LangChain 팀이 만든 에이전트 오케스트레이션 프레임워크이다.",
    "LangGraph는 상태(State), 노드(Node), 엣지(Edge) 3가지 요소로 구성된다.",
    "LangGraph의 Checkpointer(체크포인터)는 대화의 상태를 저장하여 단기 기억을 구현한다.",
    "ReAct는 Reasoning + Acting의 약자로, 추론과 행동을 번갈아 수행하는 에이전트 패턴이다.",
    "RAG는 Retrieval-Augmented Generation의 약자로, 검색 + 생성을 결합한 기법이다.",
    "Human-in-the-Loop은 AI의 작업에 사람이 개입하여 검토·승인하는 패턴이다.",
    "Python은 1991년 귀도 반 로섬이 만든 프로그래밍 언어이다.",
    "Supervisor 패턴은 관리자 에이전트가 전문 에이전트들에게 작업을 분배하는 멀티 에이전트 구조이다.",
]


# ── 노드 1: 검색 (Retrieval) ───────────────────────────────
# 이론 강의 8장 ②: "문서 DB에서 유사한 문서 검색"
def retrieve(state: RAGState) -> dict:
    query = state["question"]
    # 간단한 키워드 매칭 검색 (실무에서는 벡터 유사도 검색)
    keywords = query.replace("?", "").replace("이", "").split()
    relevant = [
        doc for doc in KNOWLEDGE_BASE
        if any(kw in doc for kw in keywords)
    ]
    if not relevant:
        relevant = ["관련 문서를 찾지 못했습니다."]
    print(f"  [retrieve] {len(relevant)}개 문서 검색됨")
    return {"documents": relevant}


# ── 노드 2: 답변 생성 (Generation) ─────────────────────────
# 이론 강의 8장 ③④: "검색된 문서를 LLM에게 참고 자료로 전달"
def generate(state: RAGState) -> dict:
    context = "\n".join(f"- {doc}" for doc in state["documents"])

    # LLM에게 "이 참고 자료만 보고 답해"라고 지시
    # → 할루시네이션(이론 강의 10장) 방지
    prompt = f"""아래 참고 자료만을 바탕으로 질문에 답하세요.
참고 자료에 없는 내용은 "해당 정보가 없습니다"라고 답하세요.

[참고 자료]
{context}

[질문]
{state['question']}

[답변]"""
    response = llm.invoke(prompt)
    return {"answer": response.content}


# ── 그래프 조립 ─────────────────────────────────────────────
graph = StateGraph(RAGState)
graph.add_node("retrieve", retrieve)
graph.add_node("generate", generate)
graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "generate")
graph.add_edge("generate", END)

app = graph.compile()


# ── 테스트 ──────────────────────────────────────────────────
questions = [
    "LangGraph의 Checkpointer가 뭐야?",
    "ReAct 패턴을 설명해줘",
    "Supervisor 패턴은 어떤 구조야?",
    "양자 컴퓨터의 원리는?",  # ← 문서에 없는 질문 (할루시네이션 테스트)
]

for q in questions:
    print(f"\n질문: {q}")
    result = app.invoke({"question": q, "documents": [], "answer": ""})
    print(f"답변: {result['answer']}")
    print("-" * 60)

제12장. 멀티 에이전트 — Supervisor 패턴

이론 연결: 이론 강의 7장(멀티 에이전트 아키텍처①: Supervisor)을 구현한다.
이론 강의에서 배웠다: *"팀장이 팀원에게 업무를 나눠주고, 결과를 모아서 보고서를 쓰는 구조"*

12-1. 구현

# ============================================================
# 실습 12-1: Supervisor 멀티 에이전트
# 이론 강의 7장 아키텍처①:
#   [Supervisor 관리자] → 작업을 전문 에이전트에게 분배
# 이론 강의 7장 소통 방식①: "공유 상태"를 사용
# ============================================================

from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Literal


class TeamState(TypedDict):
    task: str           # 원래 작업 지시
    assigned_to: str    # 배정된 에이전트
    result: str         # 작업 결과


# ── Supervisor 노드: 누구에게 맡길지 결정 ───────────────────
# 이론 강의 7장: "관리자가 작업을 분배한다"
# 실무에서는 이 판단을 LLM이 하지만, 여기서는 키워드 기반으로 단순화
def supervisor(state: TeamState) -> dict:
    task = state["task"]
    if "검색" in task or "조사" in task or "뉴스" in task:
        assigned = "researcher"
        print(f"  [Supervisor] '{task}' → 리서처에게 배정")
    elif "코드" in task or "프로그램" in task or "개발" in task:
        assigned = "coder"
        print(f"  [Supervisor] '{task}' → 코더에게 배정")
    elif "번역" in task or "영어" in task or "한국어" in task:
        assigned = "translator"
        print(f"  [Supervisor] '{task}' → 번역가에게 배정")
    else:
        assigned = "researcher"  # 기본값
        print(f"  [Supervisor] '{task}' → 리서처에게 배정 (기본)")
    return {"assigned_to": assigned}


# ── 전문 에이전트 노드들 ────────────────────────────────────
# 이론 강의 7장: "전문 분야별로 에이전트를 나눈다"
def researcher(state: TeamState) -> dict:
    result = f"[리서처] '{state['task']}'에 대해 조사 완료:\n  - AI 에이전트 시장 525억 달러 전망\n  - 기업 도입률 57% 돌파"
    return {"result": result}

def coder(state: TeamState) -> dict:
    result = f"[코더] '{state['task']}' 코드 작성 완료:\n  - main.py (150줄)\n  - 단위 테스트 3개 통과"
    return {"result": result}

def translator(state: TeamState) -> dict:
    result = f"[번역가] '{state['task']}' 번역 완료:\n  - 원문 → 번역본 생성\n  - 자연스러운 표현으로 교정"
    return {"result": result}


# ── 라우팅 함수 ─────────────────────────────────────────────
def route_task(state: TeamState) -> Literal["researcher", "coder", "translator"]:
    return state["assigned_to"]


# ── 그래프 조립 ─────────────────────────────────────────────
graph = StateGraph(TeamState)
graph.add_node("supervisor", supervisor)
graph.add_node("researcher", researcher)
graph.add_node("coder", coder)
graph.add_node("translator", translator)

graph.add_edge(START, "supervisor")
graph.add_conditional_edges("supervisor", route_task)  # 조건부 분기
graph.add_edge("researcher", END)
graph.add_edge("coder", END)
graph.add_edge("translator", END)

app = graph.compile()


# ── 테스트 ──────────────────────────────────────────────────
test_tasks = [
    "AI 최신 트렌드 조사해줘",
    "계산기 프로그램 개발해줘",
    "이 보고서를 영어로 번역해줘",
    "주말 날씨 검색해줘",
]

for task in test_tasks:
    print(f"\n작업: {task}")
    result = app.invoke({"task": task, "assigned_to": "", "result": ""})
    print(result["result"])
    print("=" * 60)

제13장. Plan-and-Execute — 계획 후 실행

이론 연결: 이론 강의 8장(고급 패턴 — Plan-and-Execute)을 구현한다.
ReAct가 "한 걸음씩 생각하며 진행"하는 방식이라면, Plan-and-Execute는 먼저 전체 계획을 세운 뒤 단계별로 실행하는 방식이다. 복잡한 다단계 작업에서 길을 잃지 않는다는 장점이 있다.

13-1. 개념

[목표 입력] → [Planner: 전체 계획 수립]
                   ↓
            [1단계 실행] → [2단계 실행] → [3단계 실행]
                   ↓
            [모든 단계 완료?] ──아니오──→ 다음 단계로
                   ↓ 예
              [최종 결과 종합]

핵심은 Planner(계획 수립)와 Executor(단계 실행)의 역할 분리다. Planner가 작업을 잘게 나눠 목록을 만들면, Executor가 그 목록을 하나씩 처리한다.

13-2. 구현

# ============================================================
# 실습 13-2: Plan-and-Execute 에이전트
# 이론 강의 8장: 먼저 계획을 세우고(Plan), 단계별로 실행(Execute)
#   [Planner] → 작업을 단계 목록으로 분해
#   [Executor] → 각 단계를 순서대로 실행
# ============================================================

from langgraph.graph import StateGraph, START, END
from typing import TypedDict


# ── 상태 정의 ──────────────────────────────────────────────
# plan: 실행할 단계들의 목록
# past_steps: 이미 완료한 단계와 그 결과
# step_index: 현재 실행 중인 단계 번호
class PlanExecuteState(TypedDict):
    goal: str                # 사용자의 최종 목표
    plan: list               # 단계 목록 (Planner가 채움)
    past_steps: list         # 완료된 단계 결과
    step_index: int          # 현재 단계 인덱스
    final_answer: str        # 최종 종합 결과


# ── Planner 노드: 목표를 단계로 분해 ────────────────────────
# 실무에서는 LLM이 계획을 세우지만, 여기서는 키워드 기반으로 단순화
def planner(state: PlanExecuteState) -> dict:
    goal = state["goal"]
    # LLM이 목표를 보고 단계 목록을 생성하는 부분 (여기서는 예시 고정)
    plan = [
        "관련 자료 검색",
        "핵심 내용 분석",
        "결과 요약 정리",
    ]
    print(f"  [Planner] 목표 '{goal}'를 {len(plan)}단계로 분해:")
    for i, step in enumerate(plan, 1):
        print(f"      {i}. {step}")
    return {"plan": plan, "past_steps": [], "step_index": 0}


# ── Executor 노드: 현재 단계 실행 ───────────────────────────
def executor(state: PlanExecuteState) -> dict:
    idx = state["step_index"]
    step = state["plan"][idx]
    # 실제로는 도구 호출이나 LLM 처리가 들어가는 부분
    result = f"'{step}' 실행 완료"
    print(f"  [Executor] {idx + 1}단계 — {result}")
    past = state["past_steps"] + [result]
    return {"past_steps": past, "step_index": idx + 1}


# ── 라우팅: 모든 단계를 끝냈는지 판단 ───────────────────────
# 남은 단계가 있으면 executor로 돌아가고(루프), 없으면 종합으로 간다
def should_continue(state: PlanExecuteState) -> str:
    if state["step_index"] < len(state["plan"]):
        return "executor"      # 아직 단계가 남음 → 계속 실행
    return "synthesize"        # 모든 단계 완료 → 결과 종합


# ── 종합 노드: 모든 단계 결과를 합쳐 최종 답변 생성 ──────────
def synthesize(state: PlanExecuteState) -> dict:
    steps_summary = "\n".join(
        f"  {i + 1}. {r}" for i, r in enumerate(state["past_steps"])
    )
    answer = f"[최종 결과] 목표 '{state['goal']}' 달성\n{steps_summary}"
    print(f"  [Synthesize] 모든 단계 종합 완료")
    return {"final_answer": answer}


# ── 그래프 조립 ─────────────────────────────────────────────
graph = StateGraph(PlanExecuteState)
graph.add_node("planner", planner)
graph.add_node("executor", executor)
graph.add_node("synthesize", synthesize)

graph.add_edge(START, "planner")
graph.add_edge("planner", "executor")
# executor 실행 후 should_continue로 분기 (루프 또는 종료)
graph.add_conditional_edges("executor", should_continue)
graph.add_edge("synthesize", END)

app = graph.compile()


# ── 테스트 ──────────────────────────────────────────────────
result = app.invoke({
    "goal": "AI 에이전트 시장 보고서 작성",
    "plan": [],
    "past_steps": [],
    "step_index": 0,
    "final_answer": "",
})

print("\n" + "=" * 60)
print(result["final_answer"])
ReAct vs Plan-and-Execute: ReAct(7장)는 매 단계마다 "다음에 뭘 할까?"를 그때그때 판단한다. 반면 Plan-and-Execute는 시작할 때 전체 계획을 한 번에 세우므로, 단계가 많고 복잡한 작업에서 더 안정적이다. 다만 도중에 상황이 바뀌면 계획을 수정해야 하는 부담이 있다.
