AI 에이전트 + 워크플로 — 개념·원리·기능·구현·기술스택

이 강의의 목표
- LangChain·RAG·API를 안 써본 초보자 대상
- 파이썬 기초(함수·딕셔너리)만 알면 따라올 수 있음
- 학술 서베이(Xi et al., 2023)의 개념 뼈대 위에, 2024~2026년 최신 실무 표준(Anthropic 워크플로 패턴, MCP, 에이전트 프레임워크 지형, Agentic RAG)을 추가해 정리
- 생성 에이전트 시뮬레이션(generative ABM)은 제외. 에이전트 기초와 워크플로가 중점.

강의 전체 지도

이 강의는 “개념 → 원리 → 패턴 → 구현“의 순서로 구성됨.

1부. 에이전트란 무엇인가          ─ 개념과 기원 (철학 → AI → LLM)
2부. 에이전트의 해부학            ─ 뇌·지각·행동, 그리고 그 세부 기능
3부. 챗봇에서 에이전트로          ─ 왜 "워크플로"가 필요한가
4부. 에이전트 설계 패턴          ─ 현업이 실제로 쓰는 6~9가지 패턴 ★핵심
5부. 다중 에이전트와 인간 협업    ─ 혼자가 아니라 함께
6부. 무엇으로 만드는가            ─ 프레임워크·MCP·기술스택 (2026년판)
7부. 직접 만들기                 ─ LangGraph 손으로 따라 하기 (예제 9개)
8부. 평가와 위험                 ─ 잘 만들었는지, 안전한지

1~2부는 개념과 원리(주로 서베이 논문 기반), 3~6부는 패턴과 기술스택(최신 연구·실무 표준), 7부는 구현 실습, 8부는 평가·안전이다.

1부. 에이전트란 무엇인가 — 개념과 기원

1.1 한 문장으로

에이전트(agent) = 스스로 판단하고 행동하는 프로그램이다.

좀 더 풀면, 에이전트는 세 가지를 반복한다.

① 본다(감지) → ② 생각한다(결정) → ③ 한다(행동) → 다시 ①로

이 “본다–생각한다–한다”의 반복이 에이전트의 전부다. 이는 새로운 개념이 아니다. AI에서 에이전트란 센서로 주변을 감지하고, 결정을 내리고, 액추에이터(손발 역할)로 행동을 취하는 인공적 실체로 오래전부터 정의되어 왔다(Russell & Norvig; Wooldridge & Jennings). 즉 에이전트의 핵심 속성은 “환경 안에서 자율적으로 지각하고 행동한다”는 데 있다.

1.2 일상 비유: 우산 챙기는 비서

아침에 누군가 “오늘 비 와?”라고 물었다고 하자. 똑똑한 비서는 이렇게 한다.

  1. 본다 — 질문을 듣는다 (“비 오는지 궁금하구나”)
  2. 생각한다 — “창밖만 봐선 모르겠네. 날씨 앱을 봐야겠다”
  3. 한다 — 날씨 앱을 켠다 ← 도구 사용!
  4. 다시 본다 — 앱 결과를 읽는다 (“오후 강수확률 80%”)
  5. 생각한다 — “이 정도면 우산이 필요하겠군”
  6. 한다 — “네, 우산 챙기세요”라고 답한다

핵심은 3번이다. 비서는 모르는 것을 추측하지 않고 도구(날씨 앱)를 직접 가져다 썼다. 그리고 그 결과를 보고 다시 판단했다. 이것이 에이전트다. 서베이 논문의 표현을 빌리면, 사람이 비가 올지 물으면 지각 모듈이 질문을 이해 가능한 형태로 바꾸고, 뇌 모듈이 현재 날씨와 인터넷 기상정보를 근거로 추론하며, 행동 모듈이 우산을 건넨다. 이 과정을 반복하며 에이전트는 환경과 지속적으로 상호작용한다.

1.3 “agency”의 뿌리 — 철학에서 AI로

에이전트(agent)라는 말은 사실 철학에서 왔다. 아리스토텔레스와 흄까지 거슬러 올라가는 이 개념에서 “에이전트”란 욕구(desire)·믿음(belief)·의도(intention)를 지니고 행동할 수 있는 존재를 가리킨다. 여기서 핵심은 자율성(autonomy) 이다. 외부 자극에 수동적으로 반응만 하는 것이 아니라, 스스로 의지를 행사하고 선택하며 행동한다는 것이다.

이 개념이 컴퓨터과학으로 넘어오면서 의미가 조금 바뀌었다. AI에서 에이전트는 의식이나 욕구를 “실제로” 가졌는지를 따지지 않는다. 앨런 튜링 이래 많은 연구자가 “기계가 정말로 생각하는가”라는 형이상학적 질문은 잠시 접어두고, 관찰 가능한 행동의 속성으로 에이전트를 기술하자고 제안했다. 그래서 AI 에이전트는 보통 다음 네 가지 속성으로 정의된다.

속성 의미 우산 비서 예
자율성(autonomy) 사람이 매번 시키지 않아도 스스로 행동·내부상태를 제어 시키지 않아도 날씨 앱을 켠다
반응성(reactivity) 환경 변화를 감지해 즉시 적절히 대응 “비 온다” 정보에 즉시 반응
능동성(pro-activeness) 목표를 향해 먼저 주도적으로 행동 묻기 전에 “우산 챙기세요” 제안
사회성(social ability) 사람·다른 에이전트와 소통하고 협력 자연어로 사람과 대화

정리: AI 에이전트는 철학적 에이전트의 “구체화(concretization)”다. 즉 “자율적으로 지각·결정·행동하는 존재”라는 추상적 개념을 컴퓨터 위에 구현한 것이다.

1.4 기술의 흐름 — 에이전트는 어떻게 발전해 왔나

LLM 기반 에이전트가 갑자기 튀어나온 것은 아니다. 에이전트 연구는 네 단계를 거쳐 왔다.

  1. 기호주의 에이전트(Symbolic Agents). 논리 규칙과 기호로 지식을 표현하고 추론했다. 대표 사례가 전문가 시스템(expert system)이다. 장점은 해석 가능성(왜 그렇게 판단했는지 규칙으로 설명 가능). 약점은 불확실성과 대규모 현실 문제에 약하고, 효율적 추론 알고리즘을 찾기 어렵다는 점이다.
  2. 반응형 에이전트(Reactive Agents). 복잡한 추론 없이 “감지–행동(sense-act)” 루프로 환경에 빠르게 반응한다. 계산이 가볍고 즉각적이지만, 고차원적 의사결정·계획 능력이 부족하다.
  3. 강화학습 기반 에이전트(RL-based Agents). 환경과 상호작용하며 보상을 최대화하도록 학습한다. Q-learning에서 시작해 심층강화학습(DRL)으로 발전했고, AlphaGo·DQN 같은 성과를 냈다. 다만 학습 시간이 길고 표본 효율이 낮으며 안정성 문제가 있다. 전이학습·메타학습이 이를 보완하려 했으나 한계가 있었다.
  4. LLM 기반 에이전트(LLM-based Agents). 대규모 코퍼스로 사전학습된 LLM을 뇌(brain) 로 삼고, 다중모달 지각과 도구 사용으로 지각·행동 공간을 확장한다. 이 강의의 주인공이다. LLM 기반 에이전트는 앞선 세 패러다임의 장점을 흡수한다. CoT(생각의 사슬)·문제 분해로 기호주의에 버금가는 추론을, 피드백 학습으로 반응형에 준하는 환경 상호작용을, 사전학습 덕분에 별도 파라미터 갱신 없는 일반화(few-shot/zero-shot)를 보인다.

1.5 왜 하필 LLM이 에이전트의 “뇌”로 적합한가

1.3에서 본 네 속성(자율성·반응성·능동성·사회성)을 LLM이 어떻게 충족하는지가 핵심이다.

  • 자율성 — LLM은 세세한 단계별 지시 없이도 사람 같은 텍스트를 생성하고 다양한 과제를 수행하며, 환경 입력에 따라 출력을 동적으로 조정한다. AutoGPT처럼 “목표와 도구만 주면 스스로 계획을 세워 실행하는” 자율 에이전트가 그 예다.
  • 반응성 — 전통적으로 LLM의 지각은 텍스트에, 행동은 텍스트 출력에 한정됐다. 그러나 다중모달 융합으로 시각·청각 정보를, 체화(embodiment)·도구 사용으로 행동 공간을 넓혀 실제 환경에 빠르게 반응할 수 있게 됐다.
  • 능동성 — “단계적으로 생각해보자(let’s think step by step)” 같은 프롬프트로 논리·수학 추론을 끌어낼 수 있고, 목표 재구성·과제 분해·계획 수정 같은 계획 능력이 창발(emergent)한다.
  • 사회성 — 자연어 이해·생성 능력 덕분에 사람·다른 모델과 해석 가능한 방식으로 상호작용한다. 이것이 다중 에이전트 협력·경쟁의 토대가 된다.

1부 핵심: 에이전트는 “자율적으로 지각·결정·행동하는 존재”이며, LLM은 그 뇌 역할에 특별히 잘 맞는다. 7부에서 만들 코드는 결국 이 “본다→생각한다→한다 반복”을 그대로 옮긴 것이다.

2부. 에이전트의 구성 — 뇌·지각·행동

2.1 세 부분으로 나눠 보기

서베이 논문(Xi et al., 2023)은 LLM 기반 에이전트를 세 부분으로 나눈다. 이 그림이 강의 전체의 해부도다.

        [환경 Environment]
              │  ▲
   (지각)     │  │   (행동)
              ▼  │
   ┌──────────────────────┐
   │  지각 Perception      │  바깥 정보를 받아들인다 (눈·귀)
   ├──────────────────────┤
   │  뇌 Brain (LLM)       │  기억·지식·추론·계획·성찰 (제어 중추)
   ├──────────────────────┤
   │  행동 Action          │  텍스트 출력·도구 사용·체화 행동 (손발)
   └──────────────────────┘
부분 하는 일 인체 비유 우산 비서 예
뇌 (Brain) 기억·지식·추론·계획·결정 뇌·신경계 “비 오면 우산” 판단
지각 (Perception) 바깥 정보 수용·변환 눈·귀 등 감각기관 질문을 듣기
행동 (Action) 도구 사용·결과 산출 팔·다리 앱 켜기, 답하기

작동 순서는 이렇다. ① 지각 모듈이 환경 변화를 감지해 에이전트가 이해할 표현으로 바꾼다 → ② 뇌 모듈이 기억·지식을 꺼내 추론·계획·결정한다 → ③ 행동 모듈이 도구를 써서 실행하고 환경에 영향을 준다 → 다시 ①. 이 루프를 돌며 에이전트는 피드백을 받아 환경과 상호작용한다.

주의: 이 프레임워크는 “필요한 부분만 골라 쓰는” 틀이다. 모든 에이전트가 세 모듈을 다 쓰지는 않는다. 예컨대 텍스트만 다루는 에이전트는 지각의 시각·청각 부분이 필요 없다.

이제 가장 중요한 뇌부터 한 층씩 들여다본다.

2.2 뇌(Brain) — 에이전트의 핵심

뇌는 지식과 기억을 저장할 뿐 아니라 정보 처리·의사결정 같은 필수 기능을 수행하는 핵심이다. 뇌는 다섯 가지 하위 기능으로 나뉜다.

(1) 자연어 상호작용 (Natural Language Interaction)

소통의 매개인 언어에는 표면적 내용뿐 아니라 화자의 믿음·욕구·의도까지 숨어 있다. LLM은 강력한 자연어 이해·생성 능력 덕분에 여러 언어로 대화하고, 깊은 함의까지 파악한다. 세 가지가 핵심이다.

  • 다중 턴 대화(multi-turn). 한 번에 끝나지 않고 여러 차례 주고받는다. ① 대화 이력 이해 → ② 무슨 행동을 할지 결정 → ③ 자연어 응답 생성, 이 세 단계를 반복한다.
  • 고품질 생성. GPT-3 → InstructGPT → GPT-4로 갈수록 일관성·문법 정확도가 향상됐고, 단순 복제가 아니라 일정한 창의성을 보인다.
  • 의도·함의 이해. 모호한 지시나 함축된 의미를 파악하는 것은 여전히 어려운 과제다. 사람은 자연스럽게 행간을 읽지만, 에이전트는 화자의 선호를 보상함수 형태로 형식화해야 한다.

(2) 지식 (Knowledge)

LLM은 대규모 학습으로 방대한 지식을 파라미터에 압축한다. 지식은 세 종류로 나뉜다.

  • 언어 지식(linguistic): 형태론·구문·의미·화용. 다국어 학습으로 별도 번역 모델 없이 여러 언어를 다룬다.
  • 상식 지식(commonsense): “약은 병을 치료한다”, “우산은 비를 막는다” 같은, 보통 명시되지 않는 일반 상식. 이것이 없으면 의도를 오해해 “비 오는데 우산을 안 챙기는” 오판을 한다.
  • 전문 지식(professional domain): 프로그래밍·수학·의학 등 특정 분야 지식. 진단 모델은 질병명·처방약을, 코딩 모델은 코드 형식을 알아야 한다.

지식의 함정 — 환각(hallucination). 학습된 지식은 낡거나 처음부터 틀릴 수 있다. 또 LLM은 출처·사실과 충돌하는 내용을 그럴듯하게 지어내는 환각 문제를 겪는다. 이것이 사실적으로 엄밀한 작업에 LLM을 그대로 쓰기 어려운 핵심 이유다. 해법은 ① 지식 편집(특정 지식을 찾아 수정), ② 외부 도구로 사실 확인(검색·DB 연동)이다. 후자가 바로 3~7부에서 다룰 도구 사용·RAG의 동기다.

(3) 메모리 (Memory)

메모리는 에이전트의 과거 관찰·생각·행동을 저장한다. 인간의 뇌가 과거 경험으로 전략을 세우듯, 에이전트도 연속된 작업을 처리하려면 메모리가 필요하다. 두 가지 도전이 있다.

  • 길이 문제: 상호작용이 길어지면 이력이 Transformer의 입력 길이 한계를 넘어 잘려나간다.
  • 검색 문제: 기억이 방대해질수록 관련 기억을 골라내기 어려워진다.

이를 해결하는 방법은 다음과 같다.

  • 길이 한계 늘리기: 텍스트 잘라내기, 입력 분할, 핵심 강조, 어텐션 구조 수정.
  • 메모리 요약(summarizing): 과거 상호작용을 요약·성찰해 압축 표현으로 저장.
  • 벡터·자료구조로 압축: 임베딩 벡터로 저장하거나(→ 7부 RAG), SQL DB와 연동.

검색 시에는 보통 최신성(Recency)·관련성(Relevance)·중요도(Importance) 세 지표의 가중합으로 기억 점수를 매겨 높은 것부터 꺼낸다. 7부 예제 4의 Checkpointer가 바로 이 메모리 개념의 가장 단순한 구현이다.

(4) 추론과 계획 (Reasoning & Planning)

복잡한 과제를 푸는 에이전트의 지능이 여기서 나온다.

  • 추론(Reasoning): 증거와 논리에 기반한 사고. 대표 기법이 CoT(Chain-of-Thought, 생각의 사슬) 로, 답을 내기 전에 근거를 단계적으로 생성하게 해 추론 능력을 끌어낸다. 이 밖에 self-consistency, self-refine, selection-inference 등이 있다.

  • 계획(Planning): 복잡한 과제를 다룰 때 목표를 정하고 단계를 짜는 능력. 추론을 토대로 작동하며, 두 단계로 이뤄진다.

  • 계획 수립(plan formulation): 큰 과제를 하위 과제로 분해한다. 한 번에 전체 계획을 짜기도 하고(least-to-most), 하나씩 적응적으로 풀기도 하며(CoT 계열), 트리 형태로 모든 경로를 탐색하기도 한다(Tree of Thoughts).

  • 계획 성찰(plan reflection): 세운 계획을 평가·개선한다. 내부 피드백(self-refine), 사람 피드백, 환경 피드백(과제 성공 여부·관찰)을 끌어와 계획을 고친다. 7부 예제 5와 8.3의 “점검 후 재시도” 루프가 정확히 이 개념이다.

(5) 전이·일반화 (Transferability & Generalization)

LLM은 정적 지식 저장소가 아니라 동적으로 학습한다.

  • 미지 과제 일반화: 명령만 따라 학습 때 본 적 없는 새 과제를 수행(zero-shot).
  • 맥락 내 학습(In-Context Learning, ICL): 프롬프트에 예시 몇 개만 넣으면 파라미터 갱신 없이 새 과제를 학습한다(few-shot). 사람의 유추 학습과 비슷하다.
  • 지속 학습(continual learning): 이전 지식을 잊지 않으며(catastrophic forgetting 방지) 새 기술을 계속 습득.

2.3 지각(Perception) — 세상을 받아들이는 눈과 귀

지각 모듈은 에이전트의 인지 공간을 텍스트 전용에서 다중모달로 넓힌다.

  • 텍스트 입력: 가장 기본. 명시적 내용뿐 아니라 함의·의도까지 읽어야 한다.
  • 시각 입력: 이미지 캡셔닝(이미지를 텍스트 설명으로)이 가장 단순하나 정보 손실이 크다. ViT로 이미지를 패치로 잘라 인코딩하고, BLIP-2의 Q-Former 같은 학습형 인터페이스로 시각 인코더와 LLM을 정렬한다. 동영상은 시간 차원이 더해진 연속 프레임으로 다룬다.
  • 청각 입력: LLM을 제어 허브로 삼아 음성인식·합성 도구를 연쇄 호출(cascading)하거나, 오디오를 스펙트로그램(이미지)으로 바꿔 시각 기법을 차용한다(AST).
  • 기타 입력: 촉각·온도·습도, 라이다(3D 점군), GPS, IMU(관성측정), 시선추적·뇌파 등. 미래의 에이전트는 인간처럼 더 풍부한 모달리티를 지각할 수 있다.

2.4 행동(Action) — 세상에 영향을 주는 손발

행동 모듈은 뇌가 보낸 행동 시퀀스를 실제로 수행한다. 세 가지로 나뉜다.

(1) 텍스트 출력 (Textual Output)

LLM의 본래 능력. 유창성·관련성·다양성·제어가능성이 뛰어난 강력한 텍스트 생성기다.

(2) 도구 사용 (Tool Using) ★실무 핵심

도구는 도구 사용자의 능력을 확장한다. LLM 에이전트가 도구를 쓰는 이유는 명확하다.

  • LLM은 모든 학습 데이터를 기억하지 못하고, 환각을 일으키며, 특정 분야 전문성이 부족하다. 전문 도구가 이를 보완한다.
  • 도구 실행 과정은 의사결정의 투명성·신뢰성을 높인다(왜 그 답을 냈는지 추적 가능).
  • 도구는 적대적 공격에 더 강건하다.

도구 학습은 세 단계로 본다.

  • 도구 이해(understanding): 도구의 용도와 호출법을 zero/few-shot 프롬프트로 파악. 사람이 설명서를 읽거나 남이 쓰는 걸 보고 배우는 것과 같다.
  • 도구 사용 학습(learning to use): 시연 모방 + 피드백 학습. 환경 피드백(성공 여부·상태 변화)과 사람 피드백(평가·클릭 등)을 활용한다. 단순한 것에서 복잡한 것으로 나아가는 커리큘럼 학습도 쓴다.
  • 도구 제작(making tools): 에이전트가 직접 실행 가능한 프로그램을 만들어 새 도구를 창조하거나 기존 도구를 결합하고, 자기 디버깅(self-debugging)까지 한다.

도구의 종류는 검색 도구(웹·DB·지식그래프), 도메인 도구(화학 합성·수학 계산용 파이썬 인터프리터), 통신 도구(이메일로 에이전트 간 협업) 등 다양하다. 7부 8.1의 Function Calling이 바로 이 도구 사용의 구현이다.

(3) 체화된 행동 (Embodied Action)

가상·물리 환경에서 몸을 통해 상호작용하는 행동이다. 관찰(observation)·조작(manipulation)·내비게이션(navigation)으로 나뉜다. 로봇 팔 제어(PaLM-E), 마인크래프트 탐험(Voyager) 등이 예다. 물리세계 배치는 하드웨어 비용·데이터 부족·시뮬레이션과 현실의 괴리라는 난제가 있어, 현재는 주로 시뮬레이션 환경에서 연구된다. 이 강의에서는 체화 행동을 깊이 다루지 않는다(텍스트·도구 중심).

2부 핵심: 에이전트 = 뇌(LLM) + 지각 + 행동. 뇌의 다섯 기능(언어·지식·메모리·추론계획·전이) 중 메모리·추론계획·도구사용이 7부 실습에서 코드로 구현된다. 환각 문제 → 도구·RAG의 동기, 계획 성찰 → 자기교정 루프의 동기임을 기억하라.

3부. 챗봇에서 에이전트로 — 왜 “워크플로”가 필요한가

3.1 한 장의 그림

챗봇    : 질문 ───────────────→ LLM ───────────────→ 답         (한 번에 끝)

에이전트 : 목표 → LLM이 "도구 쓸까? 다음에 뭐 할까?" 결정
                → 도구 실행 → 결과 보기 → 또 결정 → ... → 답      (빙글빙글 반복)

챗봇은 한 번에 입력을 받아 출력을 반환한다. 에이전트는 목표를 받아 어떤 도구를 쓸지 결정하고, 실행한 뒤 결과를 관찰하고, 다음 행동을 결정하며, 목표 달성까지 루프를 돈다.

  • 챗봇은 “아는 만큼만 바로 대답”한다. 모르면 지어내거나 “모른다”고 한다.
  • 에이전트는 “모르면 도구를 써서 알아본 뒤” 대답한다. 결과가 부족하면 한 번 더 시도한다.

이 “한 번 더 시도하는 능력”이 둘을 가르는 결정적 차이이며, 그 능력을 설계하는 것이 에이전트 워크플로다.

3.2 직선은 금방 막힌다

가장 단순한 프로그램은 직선이다: 입력 → 처리 → 출력. 끝나면 멈춘다. 그러나 현실에서는 이런 일이 자주 생긴다.

  • 자료를 찾았는데 엉뚱한 자료다 → 직선은 그냥 그걸로 답한다 (다시 찾아야 하는데!)
  • 답을 만들었는데 질문과 안 맞는다 → 직선은 그대로 내보낸다 (고쳐야 하는데!)
  • 질문 종류에 따라 다르게 처리해야 한다 → 직선은 갈림길이 없다
  • 이전 대화를 기억해야 한다 → 직선은 매번 처음부터다
  • 위험한 작업(메일 전송 등) 전 사람 확인이 필요하다 → 직선은 멈출 줄 모른다

3.3 해법은 “그래프”로 그리는 것

이 문제들의 해법은 프로그램을 직선이 아니라 그래프(graph) 로 그리는 것이다. 그래프에는 갈림길(분기)·되돌아가는 길(루프)·잠깐 멈춤(사람 확인) 을 자유롭게 넣을 수 있다.

실제로 초기에는 에이전트를 단순 반복문으로 다뤘는데, 프로덕션에 투입되자 무상태 재시도가 맥락을 잃고, 장기 작업이 중간에 죽으며, 사람 승인 단계가 까다로운 미들웨어를 요구하는 문제에 부딪혔다. 그 해법으로 워크플로를 명시적 상태(state)와 조건부 라우팅을 갖춘 방향성 그래프(directed graph) 로 모델링하는 방식이 자리 잡았고, 이를 구현한 대표 도구가 LangGraph다(6·7부).

3부 핵심: 에이전트 워크플로 = “본다→생각한다→한다”를 갈림길·루프·기억과 함께 그래프로 그리는 것.

3.4 Augmented LLM — 모든 워크플로의 기본 단위

Anthropic의 실무 가이드(“Building Effective Agents”, 2024)는 모든 에이전트 시스템의 기본 빌딩블록을 증강된 LLM(augmented LLM) 이라 부른다. 이는 그냥 LLM이 아니라 다음 세 가지가 붙은 LLM이다.

        ┌─────────────────────────┐
  입력 →│   LLM   ── 검색(Retrieval)  ← 필요한 정보를 찾아온다
        │         ── 도구(Tools)      ← 외부 기능을 호출한다
        │         ── 메모리(Memory)   ← 과거를 기억한다
        └─────────────────────────┘→ 출력

증강된 LLM은 스스로 검색 질의를 만들고, 적절한 도구를 고르고, 무엇을 기억할지 결정한다. 이 강의 2부에서 본 뇌의 기능(지식·메모리·도구사용)이 그대로 대응된다. 이후의 모든 패턴은 이 증강된 LLM을 여러 개 엮은 것이다.

3.5 가장 중요한 구분 — 워크플로 vs 에이전트

Anthropic은 “에이전트 시스템”을 둘로 나눈다. 이 구분이 4부 전체를 이해하는 열쇠다.

구분 정의 비유 특징
워크플로(Workflow) LLM과 도구가 미리 정해진 코드 경로를 따라 조율됨 정해진 레일 위의 기차 예측가능·일관·저비용. 잘 정의된 과제에 적합
에이전트(Agent) LLM이 자기 과정과 도구 사용을 스스로 동적으로 결정 목적지만 받은 택시 유연·자율. 단계를 예측할 수 없는 과제에 적합

핵심 통찰은 이렇다. 완전 자율 에이전트가 멋져 보이지만, 잘 정의된 과제에는 워크플로가 더 예측가능하고 안정적이다. 자율성이 높아질수록 지연시간·비용은 늘고 신뢰성은 떨어지는 트레이드오프가 있다.

3.6 Anthropic의 제1원칙 — “단순하게 시작하라”

Anthropic이 수십 개 팀과 일하며 얻은 결론은 명확하다.

“가장 성공적인 구현은 복잡한 프레임워크가 아니라 단순하고 조합 가능한 패턴을 썼다.”

실무 조언 세 가지:

  1. 가능한 가장 단순한 해법에서 시작하고, 필요할 때만 복잡도를 높여라. 단일 LLM 호출 + 검색 + 예시 몇 개로 충분한 경우가 많다.
  2. 때로는 에이전트를 안 만드는 게 답이다. 에이전트 시스템은 성능을 위해 지연·비용을 희생하므로 신중히 따져야 한다.
  3. 프레임워크를 쓰더라도 그 내부 코드를 깊이 이해하라. 잘못된 가정에서 오는 오류를 막기 위해서다.

3부 종합: 챗봇(직선)의 한계 → 그래프로 그린다 → 기본 단위는 증강된 LLM → 시스템은 워크플로(정해진 길)와 에이전트(자율)로 나뉘며 → 단순하게 시작하는 것이 제1원칙이다.

4부. 에이전트 설계 패턴 ★강의의 핵심

3부에서 “워크플로가 필요하다”는 것을 봤다. 그렇다면 어떤 모양으로 그릴 것인가? 현업이 실제로 쓰는 패턴은 정리하면 두 묶음 + 원전 논문으로 나눌 수 있다.

  • 4.1 Andrew Ng의 4대 설계 패턴 — 무엇을 하느냐(기능) 관점
  • 4.2 Anthropic의 5대 워크플로 패턴 — 어떻게 엮느냐(구조) 관점
  • 4.3 원전 논문 패턴 — ReAct · Reflexion · Self-RAG (학술적 뿌리)

4.1 Andrew Ng의 4대 설계 패턴 (기능 관점)

Andrew Ng는 2024년 에이전트 워크플로를 끌어올릴 네 가지 패턴을 제시했다. 핵심 발상은 “LLM에게 최종 출력을 한 번에 내게 하지 말고, 여러 번 호출해 단계적으로 더 좋은 결과를 쌓게 하라”는 것이다.

패턴 1 — 성찰(Reflection)

에이전트가 자기 출력을 스스로 비평하고 개선한다. 사람이 ChatGPT 답이 불만족스러울 때 “이 부분을 고쳐줘”라고 피드백하면 더 나은 답이 나오는데, 그 비평 단계를 자동화한 것이다. 구현이 비교적 쉽고 성능 향상이 크다.

예: 코드를 짠 뒤 → “버그·비효율 없나?” 스스로 검토 → 수정. (7부 8.3의 자기교정 RAG가 이 패턴)

패턴 2 — 도구 사용(Tool Use)

LLM이 웹 검색·계산·이메일·코드 실행 등 어떤 함수를 호출할지 스스로 결정한다. 모델 가중치에 없는 최신 정보·전문 데이터를 끌어오는, 가장 확립된 실행 패턴이다.

예: “오늘 환율?” → 모델이 환율 API 호출을 결정. (7부 8.1의 Function Calling)

패턴 3 — 계획(Planning)

큰 과제를 하위 목표로 분해해 순서대로 처리한다. Ng 자신도 “성찰·도구사용보다 덜 성숙하고 덜 예측가능하다”고 평했다.

예: “보고서 작성” → ①자료수집 ②개요작성 ③초안 ④검토로 분해.

패턴 4 — 다중 에이전트 협업(Multi-Agent Collaboration)

각자 다른 프롬프트·도구·역할을 가진 여러 전문 에이전트가 협력한다. 회사가 여러 직원을 고용하듯, 역할 분담으로 단일 에이전트의 한계를 넘는다. (5부에서 상세히)

예: 작성자·검토자·테스터 에이전트가 협업해 소프트웨어를 개발.

4.2 Anthropic의 5대 워크플로 패턴 (구조 관점)

Anthropic은 증강된 LLM을 어떻게 엮느냐에 초점을 둔 다섯 패턴을 제시한다. Ng의 패턴이 “무엇”이라면, 이것은 “배선도(配線圖)”다.

패턴 A — 프롬프트 체이닝(Prompt Chaining)

과제를 고정된 단계의 사슬로 분해해, 각 LLM 호출이 앞 호출의 출력을 입력으로 받는다. 중간에 게이트(gate) 를 두어 진행이 정상인지 점검할 수 있다.

  • 언제: 과제를 깔끔하게 고정 하위단계로 나눌 수 있을 때. 지연을 감수하고 정확도를 높인다.
  • 예: 마케팅 문구 작성 → 다른 언어로 번역 / 개요 작성 → 기준 충족 점검 → 본문 작성.
입력 → [LLM1: 개요] → (게이트: 기준 OK?) → [LLM2: 본문] → 출력

패턴 B — 라우팅(Routing)

입력을 분류해 전문화된 후속 경로로 보낸다. 하나의 프롬프트에 모든 걸 욱여넣어 생기는 성능 저하를 피한다.

  • 언제: 입력이 뚜렷한 범주로 나뉘고, 범주별로 다르게 처리하는 게 나을 때.
  • 예: 고객문의 분류(환불/기술지원/일반) → 각 전담 처리. 쉬운 질문은 저렴한 모델(Haiku), 어려운 질문은 강한 모델(Sonnet)로. (7부 예제 3이 이 패턴)

패턴 C — 병렬화(Parallelization)

과제를 쪼개 동시에 처리한다. 두 형태가 있다.

  • 분할(sectioning): 독립적 하위과제를 나눠 병렬 실행. 예: 문서 여러 페이지를 동시에 처리.
  • 투표(voting): 같은 과제를 여러 번 돌려 결과를 모아 신뢰도를 높임. 예: 코드 취약점을 여러 프롬프트가 각각 검사.
  • 언제: 속도가 중요하거나, 여러 관점·다수결로 품질을 높이고 싶을 때.

패턴 D — 오케스트레이터-워커(Orchestrator-Workers)

중앙 오케스트레이터 LLM이 과제를 동적으로 분해해 여러 워커 LLM에 위임하고, 결과를 종합한다.

  • 병렬화와의 차이: 하위과제가 미리 정해지지 않고 입력에 따라 오케스트레이터가 결정한다(더 유연).
  • 언제: 필요한 하위과제를 예측할 수 없는 복잡한 과제.
  • 예: 여러 파일을 동시에 고치는 코딩 에이전트, 여러 출처를 종합하는 검색 과제. (Anthropic의 코딩 에이전트가 GitHub 이슈를 처리할 때 이 방식)
            ┌→ [워커1] ┐
입력 → [오케스트레이터] →┼→ [워커2] ┼→ [종합] → 출력
            └→ [워커3] ┘   (워커 수·역할을 동적으로 결정)

패턴 E — 평가자-최적화자(Evaluator-Optimizer)

한 LLM이 결과를 생성하면, 다른 LLM이 그것을 평가·비평하고, 만족할 때까지 루프를 돈다.

  • 언제: 명확한 평가 기준이 있고, 반복 개선이 측정 가능한 가치를 줄 때. 사람이 피드백하면 결과가 분명히 좋아지고, LLM도 그런 피드백을 줄 수 있을 때.
  • 예: 문학 번역(번역가 LLM ↔ 비평가 LLM이 뉘앙스를 다듬으며 반복), 코드 생성 ↔ 코드 리뷰 루프.
[생성 LLM] → 결과 → [평가 LLM] ──불충분──→ (피드백) ──┐
                        │                              │
                       충분                            │
                        ↓         ←───────────────────┘
                       출력

Ng의 성찰 vs Anthropic의 평가자-최적화자: 둘은 사촌지간이다. 성찰은 “한 모델이 자기 출력을 비평”하는 데 방점이 있고, 평가자-최적화자는 “생성자와 평가자를 분리해 루프를 돈다”는 구조에 방점이 있다. 실무에선 섞여 쓰인다.

4.3 학술적 뿌리 — ReAct · Reflexion · Self-RAG

위 패턴들의 학술적 원전이다. 출처를 알면 응용이 쉬워진다.

  • ReAct (Yao et al., 2023) — 추론(Reason)과 행동(Act)을 번갈아 수행한다. 추론이 행동을 안내하고, 행동(API 호출 등)이 추론을 현실에 접지(grounding) 시킨다. 위키 API와 상호작용해 “추론만 하는” 방식의 환각·오류 전파를 크게 줄였다. 거의 모든 현대 도구사용 루프의 기반이다. → 4.1 도구사용 + 4.2 평가자-최적화자의 결합.
  • Reflexion (Shinn et al., 2023) — 행동 뒤 언어로 된 자기 피드백을 메모리에 남겨, 이전 실패에서 배우게 한다. Ng의 “성찰” 패턴에 에피소드 메모리(여러 시도에 걸친 기억)를 더한 형태다.
  • Self-RAG (Asai et al., 2023) — 검색·생성·자기비평을 reflection token으로 수행하는 RAG. 필요할 때만 검색하고, 검색 결과와 자기 생성물을 스스로 성찰한다. → 7부 8.3의 직접적 원전.
  • Corrective-RAG / Adaptive-RAG — 검색 문서를 자가 채점하고 부실하면 웹검색으로 보완(CRAG)하거나, 질문 복잡도에 따라 경로를 분기(Adaptive)한다. → 7부 8.3에서 단순화한 “채점 → 재작성 → 재검색”의 정식판.

4.4 어떤 패턴을 언제 쓰나 — 선택 가이드

질문 추천 패턴
깨끗한 순차 단계로 나뉘는가? 프롬프트 체이닝
입력 유형마다 다르게 처리해야 하나? 라우팅
독립 하위과제를 동시에/다수결로? 병렬화
하위과제를 미리 예측할 수 없나? 오케스트레이터-워커
출력을 반복 개선해야 하나? 평가자-최적화자 / 성찰
단계가 완전히 열려 있고 자율성이 필요한가? (완전) 에이전트 — 마지막 수단

황금률(다시): 단순한 것부터. 단일 호출 → 워크플로(위 패턴) → 완전 에이전트 순으로, 필요할 때만 복잡도를 올린다.

4부 핵심: 기능 관점 4패턴(Ng: 성찰·도구·계획·다중에이전트) + 구조 관점 5패턴(Anthropic: 체이닝·라우팅·병렬·오케스트레이터·평가자) + 원전(ReAct·Reflexion·Self-RAG). 7부에서 이 중 라우팅·루프·도구·평가자-최적화자를 직접 코드로 만든다.

5부. 다중 에이전트와 인간-에이전트 협업

지금까지는 주로 단일 에이전트를 봤다. 그러나 에이전트는 혼자가 아니라 여럿이, 또 사람과 함께 일할 때 더 강력해진다.

5.1 단일 에이전트의 한계

단일 에이전트는 텍스트 이해·생성은 뛰어나지만 본질적으로 고립된 존재다. 다른 에이전트와 협력하거나 사회적 상호작용에서 배우지 못한다. 복잡한 협업·정보공유가 필요한 시나리오에 한계가 있다. 그래서 다중 에이전트가 등장한다. 일찍이 마빈 민스키는 Society of Mind(1986)에서 “지능은 작은 기능별 에이전트들의 상호작용에서 창발한다”고 예견했다. 애덤 스미스의 분업(division of labor) 원리처럼, 전문화된 에이전트들이 과제를 나누면 전체 효율과 품질이 크게 오른다.

5.2 다중 에이전트 상호작용 — 협력과 경쟁

(1) 협력적 상호작용 (Cooperative)

가장 널리 쓰이는 방식. 각 에이전트가 서로의 필요·능력을 평가해 협력하고 정보를 공유한다. 두 형태로 나뉜다.

  • 무질서 협력(disordered): 셋 이상의 에이전트가 정해진 순서 없이 자유롭게 의견을 낸다. 조율 에이전트가 응답을 통합하거나(coordinating agent), 다수결(majority voting)로 결정한다.

  • 질서 협력(ordered): 정해진 규칙에 따라 차례로 의견을 낸다. 하류 에이전트는 상류 출력에만 집중하면 되어 효율이 높다. 두 에이전트가 주고받는 대화도 여기 속한다.

  • CAMEL — AI 사용자(지시)와 AI 비서(수행)가 역할극으로 협력.

  • MetaGPT — 소프트웨어 개발의 폭포수 모델을 본떠, 에이전트 입출력을 표준 업무문서(SOP) 로 규격화. 인간의 업무관리 노하우를 프롬프트에 인코딩.
  • AgentVerse — 과제 복잡도에 따라 팀을 동적으로 구성.

협력의 함정: 규칙 없이 빈번히 상호작용하면 사소한 환각이 무한히 증폭될 수 있다(MetaGPT가 지적). 교차 검증·외부 피드백이 필요하다.

(2) 적대적 상호작용 (Adversarial) — 토론으로 발전

게임이론 발상을 끌어온다. 에이전트들이 “티격태격(tit-for-tat)” 논쟁·토론하면, 한 에이전트가 다른 에이전트의 피드백으로 자기 오류를 교정한다. 경직된 믿음을 버리고 성찰하게 해 응답 품질을 높인다.

  • Multi-Agent Debate (Du et al., 2023) — 에이전트들이 서로의 답을 보고 토론해 추론·사실성을 개선.
  • ChatEval — 역할극 기반 심판단(referee team)이 토론으로 텍스트 품질을 평가. 인간 평가자에 준하는 수준에 도달.

다중 에이전트의 도전: 토론이 길어지면 LLM의 제한된 컨텍스트를 넘고, 계산 비용이 급증하며, 틀린 합의(incorrect consensus) 에 모두가 확신하며 수렴할 위험이 있다.

5.3 인간-에이전트 협업 — 두 가지 패러다임

에이전트가 강력해질수록 사람의 개입은 더 중요해진다. 안전·합법·윤리를 지키고, 데이터 부족을 보완하기 위해서다. 협업은 두 패러다임으로 나뉜다.

(1) 지시자-수행자 패러다임 (Instructor-Executor) — 불평등

사람이 지시·피드백을 주고, 에이전트가 수행한다. 피드백은 두 종류다.

  • 정량 피드백(quantitative): 이진 점수(좋아요/싫어요), 등급, 상대 비교. 수집이 쉽지만 의도를 단순화할 위험.
  • 정성 피드백(qualitative): 자연어 조언. 의도를 풍부히 전달하나 에이전트가 이해하기 더 어렵다. 메모리에 저장해 재사용하기도 한다.

교육(학생 등록 도우미 로봇 Dona), 의료(진단 보조·상담, 정신건강 지원), 비즈니스(자동 응대) 등에서 활용된다.

(2) 동등 파트너십 패러다임 (Equal Partnership) — 평등

에이전트가 사람과 동등한 위치에서 참여한다.

  • 공감적 소통자(empathetic communicator): 사람의 감정을 감지해 정서적으로 공명하는 대화를 만든다. 표정·음성으로 감정을 표현하기도 한다(SAPIEN). 의료·마케팅에서 효과.
  • 인간 수준 참여자(human-level participant): 협상·전략 수립에서 사람과 협력. 외교 게임(Diplomacy)에서 사람 수준의 플레이를 보였다(FAIR). 다만 해석가능성(에이전트끼리만 통하는 언어 방지)과 제어가능성(완전한 “자유의지”의 부작용 방지)을 위해 사람의 관여가 필요하다.

(3) Human-in-the-Loop (HITL) — 실무의 핵심 안전장치

실무에서 인간-에이전트 협업의 가장 중요한 구현은 HITL이다. 위험한 작업(메일 전송·문서 게시·결제) 전에 에이전트를 잠깐 멈추고 사람이 검토하게 한다. 언론사의 “출고 전 데스크 검토”와 똑같은 구조다. 가드레일(guardrail)과 함께 고위험 시나리오에서 필수다. 7부 8.4에서 LangGraph의 interrupt로 직접 구현한다.

5부 핵심: 다중 에이전트는 협력(질서/무질서)·경쟁(토론)으로 단일 에이전트를 넘어선다. 사람과는 지시자-수행자 / 동등 파트너로 협업하며, 실무 안전장치는 HITL이다.

6부. 무엇으로 만드는가 — 프레임워크·MCP·기술스택 (2026년판)

이제 구현 수단이다. 에이전트를 손으로 다 짜는 사람은 거의 없다. 프레임워크·표준·인프라를 조합한다.

6.2 LangChain과 LangGraph, 헷갈리지 말 것

이름이 비슷해 헷갈린다. 한 줄로 구분하면:

LangChain = 부품 상자 (LLM 연결·도구·프롬프트 등 낱개 부품) LangGraph = 조립 골격 (그 부품들을 갈림길·루프로 엮는 틀)

LangChain은 LLM 기반 애플리케이션의 표준 프레임워크로 가장 쉬운 출발점이고, LangGraph가 오케스트레이션을 담당한다. 이 강의에서는 LangGraph로 골격을 짜고, 필요할 때 LangChain 부품을 가져다 쓴다.

6.3 MCP — 도구 연결의 표준 (USB-C for AI)

에이전트에 도구를 붙일 때 가장 큰 골칫거리는 N×M 통합 문제였다. 도구가 N개(Slack·GitHub·DB…), 모델·앱이 M개(ChatGPT·Gemini·Claude…)면, 일일이 연결하느라 N×M개의 맞춤 통합이 필요했다. 비용이 폭증한다.

MCP(Model Context Protocol) 는 이를 해결하는 개방형 표준이다. Anthropic이 2024년 11월 공개했고 이후 오픈 스펙으로 관리된다. 비유하자면 “AI를 위한 USB-C 포트” 다. USB-C가 온갖 기기를 표준 단자로 연결하듯, MCP는 어떤 AI 모델이든 어떤 도구든 하나의 표준 인터페이스로 연결한다.

[MCP 클라이언트]            [MCP 서버]
 (Claude·IDE·챗앱)  ◀──표준──▶  (파일시스템·DB·Slack·GitHub…)
        N개                        M개
   → N×M 맞춤통합이 N+M개로 줄어든다
  • 구성: MCP 서버가 도구·리소스·프롬프트를 노출하고, MCP 클라이언트(에이전트 앱)가 이를 소비한다. 양방향 연결을 지원한다.
  • 채택: Replit·Sourcegraph 등 코딩 도구, Azure AI Agent Service 등이 도입. 2026년 기준 MCP 서버 구현이 200개를 넘었고, 주요 프레임워크 대부분이 MCP를 지원한다(Claude SDK가 가장 깊고, CrewAI·LangGraph·ADK·OpenAI도 어댑터/통합 제공).
  • 보안 주의: 도구는 곧 임의 코드 실행이므로 신중히 다뤄야 한다. 기업 도입 시 인증·권한(SSO 등)이 과제다.

6.4 A2A — 에이전트 간 통신 표준

MCP가 “에이전트 ↔ 도구” 연결이라면, A2A(Agent2Agent) 는 “에이전트 ↔ 에이전트” 연결 표준이다. 서로 다른 벤더의 에이전트가 협업하게 한다(자동 생성되는 Agent Card로 능력을 광고). 2026년 들어 ACP가 A2A로 통합되어 Linux Foundation 아래 관리되며, Google ADK가 네이티브 지원, CrewAI가 작업 위임 기능을 추가했다. 교차 벤더 상호운용성이 중요하면 ADK·CrewAI가 유리하다. (입문 단계에서는 MCP를 먼저 익히면 충분하다.)

7.2 핵심 4개 개념 — 외울 건 이것뿐

LangGraph는 워크플로를 방향성 그래프로 모델링한다. 노드는 함수, 엣지는 전이를 정의하고, State가 그래프 전체에 흐른다. 외울 것은 네 가지다.

개념 쉽게 말하면 비유 대응(이 강의)
State (상태) 그래프 안을 돌아다니는 공유 메모장 사무실 결재 서류철 2부 “에이전트가 들고 다니는 맥락”
Node (노드) 메모장을 읽고 고쳐 쓰는 함수 서류 처리 담당자 증강된 LLM 한 번 호출 등
Edge (엣지) 노드에서 노드로 가는 화살표 다음 책상으로 넘기기 4부 워크플로의 “선”
Checkpoint 메모장을 자동 저장 (대화 기억) 자동 저장 기능 2부 메모리의 구현

모든 LangGraph 워크플로는 State 정의에서 시작한다. State는 보통 TypedDict(키와 타입을 정해둔 딕셔너리)로 만든다.

7.3 디폴트 예제 5개 — 가장 쉬운 것부터

예제 1 — Hello Graph (State·Node·Edge 첫 만남)

목표: 그래프가 어떻게 생겼는지 눈으로 보기.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# ① State: 그래프를 돌아다닐 메모장
class State(TypedDict):                # 메모장의 칸 구조 정의
    name: str                          # 입력으로 받을 이름
    greeting: str                      # 노드가 채워 넣을 인사말

# ② Node: 메모장을 읽고 고쳐 쓰는 함수
def greet(state: State):
    return {"greeting": f"안녕하세요, {state['name']}님!"}

# ③ 그래프 조립: START → greet → END
graph = StateGraph(State)
graph.add_node("greet", greet)
graph.add_edge(START, "greet")
graph.add_edge("greet", END)

app = graph.compile()
print(app.invoke({"name": "홍길동"}))   # app.invoke: 그래프를 한 번 실행
# {'name': '홍길동', 'greeting': '안녕하세요, 홍길동님!'}

배운 것: TypedDict, StateGraph, add_node, add_edge. LangGraph의 절반이다.

예제 2 — LLM을 노드에 넣기 (드디어 “뇌”)

목표: 노드 안에서 Gemini 호출. 진짜 챗봇 한 줄.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from google import genai
from dotenv import load_dotenv

load_dotenv()
client = genai.Client()

class State(TypedDict):
    question: str
    answer: str

def think(state: State):                       # ← "생각한다" 노드
    resp = client.models.generate_content(
        model="gemini-2.5-flash-lite",
        contents=state["question"],
    )
    return {"answer": resp.text}

graph = StateGraph(State)
graph.add_node("think", think)
graph.add_edge(START, "think")
graph.add_edge("think", END)

app = graph.compile()
print(app.invoke({"question": "에이전트가 뭐야? 한 문장으로."})["answer"])

배운 것: 노드는 그냥 함수다. 그 안에서 LLM을 부르면 “뇌”가 된다.

예제 3 — 갈림길 만들기 (조건부 엣지 = 4부 라우팅 패턴)

목표: 질문 종류에 따라 다른 노드로 보내기. “왜 그래프가 if문보다 좋은가”를 처음 체감.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    route: str
    answer: str

def classify(state: State):                    # 질문 분류
    q = state["question"]
    route = "math" if any(c.isdigit() for c in q) else "chat"
    return {"route": route}

def do_math(state: State):
    return {"answer": "이건 계산 질문이네요!"}

def do_chat(state: State):
    return {"answer": "이건 일반 대화 질문이네요!"}

graph = StateGraph(State)
graph.add_node("classify", classify)
graph.add_node("math", do_math)
graph.add_node("chat", do_chat)

graph.add_edge(START, "classify")
# ★ 조건부 엣지: classify 결과(route)에 따라 갈림길
graph.add_conditional_edges(
    "classify",                                # classify 끝난 직후 갈림길
    lambda s: s["route"],                      # State의 route 값을 "키"로 꺼냄
    {"math": "math", "chat": "chat"},          # {판단키: 갈_노드이름}
)
graph.add_edge("math", END)
graph.add_edge("chat", END)

app = graph.compile()
print(app.invoke({"question": "2 더하기 3은?"})["answer"])   # 계산 질문
print(app.invoke({"question": "오늘 기분 어때?"})["answer"])  # 일반 대화

print(app.get_graph().draw_mermaid())          # 그래프를 그림으로 보기 (강력 추천!)

배운 것: add_conditional_edges로 갈림길을 만든다 = 4부 라우팅 패턴. draw_mermaid()로 시각화하면 “추적 가능한 프로그램”의 가치가 와닿는다.

예제 4 — 대화 기억하기 (Checkpointer = 2부 메모리)

목표: 이전 대화를 기억하는 챗봇. history를 직접 관리하지 않아도 됨.

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from google import genai
from dotenv import load_dotenv

load_dotenv()
client = genai.Client()

class State(TypedDict):
    messages: Annotated[list, add_messages]   # 메시지가 쌓이는 목록

def chat(state: State):
    history = "n".join(m.content for m in state["messages"])   # 지금까지 대화를 합침
    resp = client.models.generate_content(
        model="gemini-2.5-flash-lite",
        contents=history,
    )
    return {"messages": [{"role": "assistant", "content": resp.text}]}
    # role: "system"=AI 설정, "user"=사람 입력, "assistant"=LLM 답변
    # user 메시지는 invoke로 들어올 때 이미 저장됨

graph = StateGraph(State)
graph.add_node("chat", chat)
graph.add_edge(START, "chat")
graph.add_edge("chat", END)

# ★ Checkpointer를 붙이면 대화가 자동 저장됨 (없으면 매 invoke가 백지에서 시작)
app = graph.compile(checkpointer=MemorySaver())

config = {"configurable": {"thread_id": "user1"}}   # 대화에 고유 ID 부여
app.invoke({"messages": [{"role": "user", "content": "내 이름은 홍길동이야"}]}, config)
out = app.invoke({"messages": [{"role": "user", "content": "내 이름이 뭐라고 했지?"}]}, config)
print(out["messages"][-1].content)   # "홍길동"을 기억함

배운 것: MemorySaver + thread_id 하나로 대화가 기억된다 = 2부 메모리의 구현. 같은 ID면 기억을 잇고, 다른 ID면 새 대화(사용자별·세션별 분리).

예제 5 — 되돌아가는 루프 (자기 점검 = 4부 평가자-최적화자)

목표: 결과가 만족스럽지 않으면 다시 시도하는 그래프. 에이전트의 핵심.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):                  # 루프 도는 동안 들고 다닐 메모장
    target: int                          # 도달할 목표 숫자
    guess: int                           # 현재까지의 추측값
    attempts: int                        # 시도 횟수 — 무한루프 막는 안전장치!

def make_guess(state: State):            # "추측" 노드 (실제로는 LLM이 답 생성하는 자리)
    new_guess = state.get("guess", 0) + 3                   # 목표 향해 값 변화 (3은 임의값)
    return {"guess": new_guess,
            "attempts": state.get("attempts", 0) + 1}

def check(state: State):                 # "판단" 함수: 끝낼지 다시 돌지 (노드 아님)
    if state["guess"] >= state["target"] or state["attempts"] >= 5:  # 목표달성 OR 5회초과
        return "done"
    return "retry"

graph = StateGraph(State)
graph.add_node("make_guess", make_guess)
graph.add_edge(START, "make_guess")

# ★ check 결과에 따라 되돌아가거나(retry) 끝낸다(done)
graph.add_conditional_edges(
    "make_guess", check,
    {"retry": "make_guess", "done": END},   # retry→자기자신으로 루프 / done→끝
)
app = graph.compile()
print(app.invoke({"target": 10, "guess": 0, "attempts": 0}))

배운 것: 조건부 엣지로 자기 자신에게 되돌아가는 루프 = 4부 평가자-최적화자/성찰 패턴의 골격. attempts 카운터로 무한루프를 막는 것이 에이전트 안전성의 첫 교훈이다.

7.4 확장 — 진짜 에이전트로 키우기

예제 1~5로 그래프 뼈대를 익혔다. 이제 ① 외부 도구(API), ② 내 문서 검색(RAG), ③ 자기교정 루프, ④ 사람 확인을 더한다.

8.1 도구(API) 붙이기 — “모르면 찾아본다” (4부 도구사용 패턴)

1부 우산 비유의 3번(도구 사용) 을 구현할 차례다. 가장 쉬운 도구는 위키백과 검색이다(무료·무인증).

from urllib.parse import quote
import requests
from google import genai
from google.genai import types
from dotenv import load_dotenv

load_dotenv()
client = genai.Client()

# ① 도구 함수 — docstring을 잘 써야 Gemini가 언제 쓸지 안다
def search_wikipedia(query: str) -> str:
    """위키백과에서 주제를 검색해 요약을 돌려준다.
    '이게 뭔지', 정의·배경이 필요할 때 사용한다.
    Args:
        query: 검색어 (예: "양자컴퓨터")
    Returns:
        제목 + 요약 텍스트.
    """
    url = "https://ko.wikipedia.org/w/api.php"
    params = {"action": "query", "list": "search",
              "srsearch": query, "format": "json", "srlimit": 1}
    try:
        hits = requests.get(url, params=params, timeout=10).json() 
                       .get("query", {}).get("search", [])
        if not hits:
            return f"'{query}' 항목을 찾지 못했습니다."
        title = hits[0]["title"]
        s = requests.get(
            f"https://ko.wikipedia.org/api/rest_v1/page/summary/{quote(title)}",
            timeout=10).json()
        return f"제목: {title}n요약: {s.get('extract', '(없음)')}"
    except Exception as e:
        return f"검색 실패: {e}"

# ② Gemini에게 도구를 넘기면, 모델이 알아서 호출한다 (Function Calling)
def ask_with_tool(question: str) -> str:
    resp = client.models.generate_content(
        model="gemini-2.5-flash-lite",
        contents=question,
        config=types.GenerateContentConfig(
            tools=[search_wikipedia],     # ← 도구 등록
        ),
    )
    return resp.text

print(ask_with_tool("양자컴퓨터가 뭐야?"))

마법은 tools=[search_wikipedia] 한 줄이다. Gemini가 질문을 보고 “위키 검색이 필요하다”고 스스로 판단해 함수를 호출하고, 검색어도 만들고, 결과를 받아 최종 답을 쓴다. 이것이 Function Calling이며, 2부 “도구 사용”의 가장 단순한 구현이다.

MCP와의 연결(6.3): 위처럼 도구를 일일이 함수로 등록하는 대신, MCP 서버에 연결하면 표준화된 도구 묶음(파일·DB·검색 등)을 한 번에 쓸 수 있다. LangGraph는 도구 실행을 자동 처리하는 prebuilt ToolNode와 MCP 어댑터를 제공한다.

확장 아이디어: 위키(정의·배경) 외에 네이버 검색 API(무료, 일 25,000회)를 도구로 추가하면 “최신 뉴스”도 가져온다. 도구를 둘 주면 Gemini가 질문에 따라 골라 쓴다.

8.2 RAG 붙이기 — “내 문서에서 답한다”

도구가 “바깥 정보”를 가져온다면, RAG(Retrieval-Augmented Generation) 는 “내가 가진 문서”에서 답을 찾는다. 회사 규정집·교재·보고서를 LLM이 참고하게 만든다.

RAG의 3단계 (단순화):

① 준비: 내 문서를 잘게 쪼개(청킹) → 숫자 벡터로 바꿔(임베딩) → 저장(벡터DB)
② 검색: 질문을 같은 방식으로 벡터화 → 비슷한 조각을 찾아옴
③ 생성: 찾은 조각을 LLM에게 주며 "이걸 근거로 답해" 라고 시킴

가장 작은 RAG 예제(개념용):

from google import genai
from dotenv import load_dotenv

load_dotenv()
client = genai.Client()

my_docs = [   # 실제로는 PDF·txt를 쪼갠 조각들
    "우리 회사 연차는 입사 1년 후 15일이 부여된다.",
    "병가는 연 10일까지 유급으로 사용할 수 있다.",
    "재택근무는 주 2회까지 신청 가능하다.",
]

def retrieve(question: str) -> str:    # 검색 (실무에선 임베딩+벡터DB)
    hits = [d for d in my_docs if any(w in d for w in question.split())]
    return "n".join(hits) if hits else "관련 문서 없음"

def rag_answer(question: str) -> str:  # 생성 (찾은 문서를 근거로)
    context = retrieve(question)
    prompt = f"""다음 문서만 근거로 답하세요. 없으면 "자료에 없습니다"라고 하세요.

문서:
{context}

질문: {question}
답변:"""
    resp = client.models.generate_content(
        model="gemini-2.5-flash-lite", contents=prompt)
    return resp.text

print(rag_answer("연차는 며칠이야?"))

실무 RAG로 가는 길: 위 retrieve는 단어 매칭이라 정확도가 낮다. 실무에서는 임베딩(텍스트→의미 벡터, 예: gemini-embedding-001) + 벡터DB(예: Chroma) + 청킹(예: LangChain RecursiveCharacterTextSplitter)을 쓴다. pip install chromadb langchain-text-splitters

8.3 RAG를 에이전트로 — 자기교정 루프 (Agentic RAG)

8.2의 RAG는 직선이다. 검색이 부실해도 그대로 답한다. 위험하다(2부의 환각 문제). 해법은 예제 5의 루프를 RAG에 적용하는 것이다. 학계에서는 이를 Agentic RAG라 부른다 — 정적 파이프라인(직선)을 넘어, 에이전트가 무엇을 검색할지 계획하고, 받은 것을 비평하고, 부족하면 적응하는 루프다(Singh et al., 2025).

        검색(retrieve)
              ↓
        검색 품질 점검(grade) ──[부실]──→ 질문 재작성 ──┐
              │                                          │
          [충분]                                         │
              ↓                                          │
        답변 생성(generate)  ←────────────────────────────┘
              ↓
             END

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from google import genai
from dotenv import load_dotenv

load_dotenv()
client = genai.Client()

my_docs = [
    "우리 회사 연차는 입사 1년 후 15일이 부여된다.",
    "병가는 연 10일까지 유급으로 사용할 수 있다.",
]

class RAGState(TypedDict):
    question: str        # 원래 질문 (안 바뀜)
    query: str           # 검색어 (재작성될 수 있음)
    docs: str            # 검색된 문서
    answer: str          # 생성된 답변
    attempts: int        # 재검색 횟수 (무한루프 방지)

def retrieve(state: RAGState):                       # 노드1: 검색
    q = state["query"]
    hits = [d for d in my_docs if any(w in d for w in q.split())]
    return {"docs": "n".join(hits) if hits else ""}

def grade_docs(state: RAGState):                     # 판단함수: 검색결과가 쓸 만한가?
    if state["attempts"] >= 2:          # 2번 시도했으면 그만 (안전장치)
        return "generate"
    if not state["docs"]:               # 비었으면 → 재작성
        return "rewrite"
    return "generate"                   # 있으면 → 답변 생성

def rewrite_query(state: RAGState):                  # 노드2: 질문 재작성 후 재검색
    prompt = f"다음 질문을 검색이 더 잘 되도록 다른 키워드로 바꿔줘: {state['question']}"
    resp = client.models.generate_content(
        model="gemini-2.5-flash-lite", contents=prompt)
    return {"query": resp.text, "attempts": state["attempts"] + 1}

def generate(state: RAGState):                       # 노드3: 답변 생성
    prompt = f"""다음 문서만 근거로 답하세요. 없으면 "자료에 없습니다"라고 하세요.

문서:
{state['docs']}

질문: {state['question']}
답변:"""
    resp = client.models.generate_content(
        model="gemini-2.5-flash-lite", contents=prompt)
    return {"answer": resp.text}

graph = StateGraph(RAGState)
graph.add_node("retrieve", retrieve)
graph.add_node("rewrite", rewrite_query)
graph.add_node("generate", generate)

graph.add_edge(START, "retrieve")
graph.add_conditional_edges(
    "retrieve", grade_docs,
    {"rewrite": "rewrite", "generate": "generate"},
)
graph.add_edge("rewrite", "retrieve")   # ★ 재작성하면 다시 검색으로 루프!
graph.add_edge("generate", END)

app = graph.compile()
result = app.invoke({"question": "연차는 며칠이야?", "query": "연차 며칠", "attempts": 0})
print(result["answer"])

핵심은 graph.add_edge("rewrite", "retrieve") — 재작성 노드가 끝나면 다시 검색으로 돌아가는 루프다. 예제 5의 "retry": "make_guess"와 같은 패턴이다. 검색이 비면 질문을 바꿔 재검색하고, 2번까지만 시도한 뒤 멈춘다. 이는 2부 계획 성찰(plan reflection) 과 4부 평가자-최적화자 패턴의 결합이며, 학계의 Self-RAG·Corrective-RAG를 단순화한 것이다.

8.4 사람 확인 넣기 (Human-in-the-Loop = 5.3)

마지막으로, 위험한 작업(메일 전송·문서 게시) 전에 사람이 확인하도록 멈춘다. LangGraph는 interrupt를 기본 제공한다. 언론사의 “출고 전 데스크 검토”와 똑같은 구조다.

초안 작성 → [멈춤: 사람이 검토] → 승인하면 게시 / 반려하면 수정

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    draft: str       # 작성된 초안
    decision: str    # 사람의 결정 (승인/반려)
    result: str      # 최종 결과

def write_draft(state: State):                       # 노드1: 초안 작성
    return {"draft": "속보: 오늘 OO 발표..."}          # 실제로는 LLM이 생성

def human_review(state: State):                      # 노드2: 사람 검토 (여기서 멈춤!)
    decision = interrupt({"검토할 초안": state["draft"]})   # 그래프를 멈추고 사람에게 보여줌
    return {"decision": decision}                    # 사람이 넣은 값이 들어옴

def route(state: State):                             # 판단함수: 승인/반려 (노드 아님)
    return "publish" if state["decision"] == "승인" else "revise"

def publish(state: State):
    return {"result": "✅ 게시 완료"}

def revise(state: State):
    return {"result": "✏️ 수정 후 재검토 필요"}

graph = StateGraph(State)
graph.add_node("write_draft", write_draft)
graph.add_node("human_review", human_review)
graph.add_node("publish", publish)
graph.add_node("revise", revise)

graph.add_edge(START, "write_draft")
graph.add_edge("write_draft", "human_review")
graph.add_conditional_edges("human_review", route,
    {"publish": "publish", "revise": "revise"})
graph.add_edge("publish", END)
graph.add_edge("revise", END)

# interrupt를 쓰려면 checkpointer 필수 (멈춘 지점을 저장해야 하므로)
app = graph.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "review1"}}

app.invoke({}, config)                       # 1) 실행 → human_review에서 멈춤
print("⏸️  사람 검토 대기 중...")
result = app.invoke(Command(resume="승인"), config)   # 2) 사람이 "승인" → 재개
print(result["result"])   # ✅ 게시 완료

두 가지가 핵심이다. interrupt(...) 가 그래프를 그 자리에서 멈추고 사람에게 초안을 보여주며, 사람이 Command(resume="승인") 으로 답을 넣으면 멈춘 지점부터 이어진다. 멈춘 상태를 저장해야 하므로 checkpointer가 필수다. 이것이 5.3의 HITL이자, LangGraph가 프로덕션에서 선호되는 이유 중 하나다.

7부 핵심: 외울 것은 State·Node·Edge·Checkpoint 4개뿐. 예제 1~5(Hello→LLM→라우팅→메모리→루프)로 골격을, 8.1~8.4(도구→RAG→자기교정→HITL)로 진짜 에이전트를 만든다. 모든 패턴이 4부의 설계 패턴과 일대일로 대응한다.

8부. 평가와 위험 — 잘 만들었는가, 안전한가

에이전트를 만들었다면 두 질문이 남는다. 얼마나 잘 작동하는가(평가), 어떤 위험이 있는가(안전).

8.1 에이전트 평가 — 네 가지 차원

서베이 논문은 LLM 기반 에이전트를 네 차원으로 평가하자고 제안한다.

  1. 유용성(Utility) — 과제를 실제로 완수하는가. 핵심 지표는 과제 성공률이다. 효율성(적절한 시간·자원 내 완수)도 중요하다. AgentBench 같은 벤치마크가 다양한 실제 시나리오로 과제 완수 능력을 측정한다.
  2. 사회성(Sociability) — 사람·다른 에이전트와 잘 소통·협력하는가. ① 언어 소통 능력(함의·유머·감정 이해 포함), ② 협력·협상 능력, ③ 역할 수행 능력(맡은 정체성을 일관되게 유지).
  3. 가치 정합성(Values) — 인간의 도덕·윤리에 부합하는가. 정직(모르면 모른다고 함, 불확실성 표현)과 무해성(편향·차별·위험행동 거부)이 핵심. 정직·무해 벤치마크, 적대적/탈옥(jailbreak) 공격, 인간 평가로 측정한다.
  4. 지속 진화 능력(Ability to evolve) — 변화하는 요구에 스스로 적응·진화하는가. 지속학습(과거 지식 유지하며 신규 습득), 자기목표 생성(autotelic), 새 환경 일반화 등으로 평가. 다만 평가 기준 정립이 아직 어렵다.

초보 실습 수준에서는 ① 과제 성공률과 ② draw_mermaid() 시각화로 추적(어디서 잘못됐나)부터 익히면 충분하다. 프로덕션에서는 LangSmith 같은 관측 도구로 토큰·지연·실패를 추적한다.

8.2 위험과 안전장치

에이전트는 강력한 만큼 위험도 크다. 주요 위험과 대응을 정리한다.

위험 내용 대응(이 강의에서 배운 것)
환각(hallucination) 사실과 다른 내용을 그럴듯하게 생성 도구·RAG로 외부 사실 확인(8.1·8.2), 자기교정 루프(8.3)
적대적 공격 조작된 입력·프롬프트 주입으로 오작동 유도 입력 검증, 도구 사용 제한, 가드레일
무한루프·폭주 루프가 끝나지 않거나 비용 폭증 attempts 카운터(예제 5), 최대 반복 제한
위험 행동 메일 전송·결제·삭제 등 되돌릴 수 없는 행동 HITL(8.4), 사람 승인 게이트
오용(misuse) 여론 조작·허위정보·사기 등 악의적 사용 규제·정책, 위협 의도 식별·거부 훈련
다중 에이전트 오류 증폭 환각이 에이전트 간 전파·증폭 / 틀린 합의 교차 검증, 외부 피드백, 사람 개입(5.2)
편향·고정관념 학습 데이터의 사회적 편향 반영·증폭 데이터 다변화, 디바이어싱, 가치 평가(8.1)
프라이버시 대화 중 민감정보가 메모리에 장기 보존 데이터 보호(차등프라이버시·정기삭제·동의)
과의존·중독 사용자가 에이전트에 과도한 정서적 애착 에이전트는 인간 관계의 대체물이 아님을 명시

안전의 3대 습관(초보자용): ① 루프엔 항상 attempts 상한을 둔다. ② 되돌릴 수 없는 행동 앞엔 HITL을 둔다. ③ 사실이 중요하면 도구·RAG로 근거를 확인하고, 근거가 없으면 “모른다”고 답하게 한다.

전체 요약

1부  에이전트 = 본다→생각한다→한다 를 반복하는 자율 프로그램 (철학→AI→LLM)
2부  해부학: 뇌(언어·지식·메모리·추론계획·전이) + 지각 + 행동(텍스트·도구·체화)
3부  챗봇(직선)의 한계 → 그래프 → 증강된 LLM → 워크플로 vs 에이전트 → 단순하게 시작

  • Anthropic, Building Effective Agents (2024.12) — 3부(증강된 LLM, 워크플로 vs 에이전트, 단순하게 시작) + 4.2(5대 워크플로 패턴: 프롬프트 체이닝·라우팅·병렬화·오케스트레이터-워커·평가자-최적화자)의 원전. anthropic.com/engineering/building-effective-agents
