RAG(Retrieval-Augmented Generation, 검색 증강 생성)

0. 이 강의에서 학습할 내용

이 강의를 마치면 다음을 직접 할 수 있게 됩니다.

  • 왜 ChatGPT 같은 대형 언어 모델(LLM)이 "방송법 제33조에 따른 심의 기준은?" 같은 구체적 질문에 자신 있게 틀린 답을 하는지 그 메커니즘을 설명할 수 있습니다.
  • 한국어 미디어 자료를 적절히 잘라(청킹) 임베딩 벡터로 변환하고 데이터베이스에 저장할 수 있습니다.
  • 새 질문이 들어오면 관련 문서를 검색해 LLM에게 함께 전달하여 근거 있는 답변을 만들어내는 챗봇을 구축할 수 있습니다.
  • Gemini 무료 API + Chroma + 파이썬만으로, GPU 없이, 노트북 한 대로 전체 시스템을 만들 수 있습니다.
  • GraphRAG·Agentic RAG 같은 최신 발전 방향이 어디서 어떻게 생겨났는지 이해할 수 있습니다.

수업을 따라가는 데 필요한 사전 지식은 파이썬 기초 문법(변수, 함수, 리스트, 딕셔너리, for문) 정도입니다.

1장. 왜 RAG가 필요한가

1.1 LLM은 통계적 앵무새다

ChatGPT, Gemini, Claude 같은 대형 언어 모델은 본질적으로 *"앞 단어들이 주어졌을 때 다음 단어가 무엇일 확률이 가장 높은가"*를 예측하는 거대한 통계 기계입니다. 인터넷의 방대한 텍스트로 훈련받아 그 확률 분포를 학습했고, 그 결과로 사람처럼 말하는 능력을 갖추게 되었습니다.

이 사실을 받아들이면 LLM의 행동이 일관되게 해석됩니다. LLM은 진실을 추구하지 않습니다. 그럴듯한 단어 배열을 생성할 뿐입니다. 대부분 그럴듯한 배열은 진실과 일치하지만, 일치하지 않을 때도 LLM은 똑같이 자신감 있게 말합니다.

1.2 환각(Hallucination)의 정체

다음 질문을 ChatGPT에 던졌다고 가정해 봅시다.

"언론중재위원회의 2023년 결정문 중 정정보도 청구가 인용된 사례 세 건을 출처와 함께 알려주세요."

ChatGPT는 매우 그럴듯한 사건 번호와 신문사명, 정정 내용을 술술 답해줄 것입니다. 그런데 그 사건 번호는 실재하지 않을 수 있습니다. 신문사명은 맞을 수 있지만 사건은 지어낸 것일 수 있습니다. 이것이 환각입니다.

환각은 LLM이 "거짓말을 한다"기보다는, 훈련 데이터에서 본 비슷한 패턴을 조합해 가장 그럴듯한 답을 만들어낼 뿐이라는 본질에서 비롯됩니다. 모델 입장에서는 "모른다"고 답하는 것보다 "그럴듯한 답"을 만드는 것이 통계적으로 더 확률 높은 출력이기 때문입니다.

1.3 컨텍스트 한계와 최신성 한계

LLM에는 두 가지 추가 제약이 있습니다.

컨텍스트 길이 한계. 한 번에 입력할 수 있는 텍스트 길이에 제한이 있습니다. Gemini 2.5 Flash는 약 1백만 토큰(대략 한국어 70만 자)까지 받지만, GPT-4o는 약 12만 8천 토큰, 무료 ChatGPT는 더 짧습니다. 방송법 전체 + 시행령 + 시행규칙 + 관련 판례 100건을 한 번에 넣는 것은 무료 도구로는 어렵습니다.

최신성 한계. LLM은 학습 시점까지의 데이터만 압니다. 어제 발표된 헌법재판소 결정이나 오늘 통과된 법안은 모릅니다.

1.4 RAG의 핵심 아이디어 — "기억"이 아닌 "검색"

RAG는 Retrieval-Augmented Generation, 한국어로 검색 증강 생성입니다. 발상의 전환은 단순합니다.

"LLM이 모든 것을 기억하도록 만들 필요가 없다. 질문이 들어왔을 때 그 질문에 답하는 데 필요한 자료만 찾아서 LLM에게 함께 던져주면 된다."

사람으로 비유하면 이렇습니다. 변호사가 의뢰인의 질문에 답할 때 모든 판례를 외우고 있지는 않습니다. 대신 관련된 판례 몇 건을 찾아 책상에 펼쳐 놓고, 그것을 참조하며 답합니다. RAG는 LLM에게 책상을 제공하는 기술입니다.

1.5 ChatGPT와 RAG 챗봇의 차이

같은 질문을 두 시스템에 던져봅시다.

"언론중재위원회가 2023년 다룬 사건 중에서 '정정보도'와 '추후보도'가 함께 청구된 사례를 찾아주세요."

시스템 답변 양상
일반 ChatGPT 그럴듯한 사례를 지어낼 가능성이 높음. 사건 번호와 신문사명이 실재하지 않을 수 있음
RAG 챗봇 (언론중재위 결정문 200건 적재) "다음 3건이 검색되었습니다: 2023-XX호(○○일보, 정정+추후), 2023-YY호..." 출처 명시 가능

이 차이가 미디어 연구와 저널리즘에서 RAG가 중요한 이유입니다.

2장. RAG의 전체 그림

2.1 두 개의 파이프라인

RAG 시스템은 두 개의 분리된 파이프라인으로 구성됩니다.

(A) 빌드 파이프라인 (사전 작업, 한 번만 실행)

원본 문서 → 청킹 → 임베딩 생성 → 벡터 DB에 저장

(B) 쿼리 파이프라인 (사용자가 질문할 때마다 실행)

사용자 질문 → 질문 임베딩 → 벡터 DB에서 유사 청크 검색 → LLM에 [질문+검색된 청크] 전달 → 답변 생성

두 파이프라인이 분리되어 있다는 점이 RAG 이해의 첫 번째 핵심입니다. 빌드는 무겁고 느려도 한 번만 하면 됩니다. 쿼리는 가볍고 빨라야 하며 매번 실행됩니다.

2.2 일상적 비유

도서관 사서를 떠올려 봅시다.

  • 빌드 파이프라인 = 책이 들어올 때마다 사서가 분류하고 색인을 만들어 서가에 꽂는 과정.
  • 쿼리 파이프라인 = 독자가 *"한국 언론의 정정보도에 관한 연구"*를 물으면, 사서가 색인을 뒤져 관련 책 3권을 찾아 독자에게 건네는 과정.

LLM은 이 비유에서 독자입니다. 책을 외우고 있지는 않지만 책을 받아 읽고 종합할 수는 있습니다. 사서(검색기)가 좋은 책을 찾아주면 좋은 답이 나오고, 엉뚱한 책을 찾아주면 엉뚱한 답이 나옵니다. RAG 시스템의 품질은 사서의 품질에 좌우됩니다.

2.3 각 단계를 미리 한 번씩 짚어보기

이후 자세히 다룰 각 단계를 일단 한 번씩 미리 만나봅시다.

  1. 청킹: 긴 문서를 작은 조각(청크)으로 자릅니다. 한 청크가 너무 크면 의미가 흐려지고, 너무 작으면 맥락을 잃습니다.
  2. 임베딩: 각 청크를 벡터(숫자 배열)로 변환합니다. 의미가 비슷한 청크는 벡터 공간에서 가까이 위치합니다.
  3. 저장: 벡터들을 벡터 DB에 넣습니다. 일반 DB가 아니라 벡터 간 거리를 빠르게 계산할 수 있도록 설계된 특수 DB입니다.
  4. 검색: 질문도 같은 방식으로 임베딩해서, 그것과 가장 가까운 청크들을 찾습니다.
  5. 생성: 찾은 청크들과 원래 질문을 함께 LLM에게 주고 답을 만들게 합니다.

3장. 임베딩 — 벡터 변환

3.1 단어를 어떻게 숫자로 표현할까

자연어 처리의 출발점은 단어를 컴퓨터가 다룰 수 있는 형태로 변환하는 것입니다. 가장 단순한 방법은 사전을 만들어 각 단어에 번호를 매기는 것입니다.

"기자" = 1, "정정보도" = 2, "보도" = 3, ...

문제는 이 방식이 의미 관계를 전혀 표현하지 못한다는 점입니다. "기자"(1)와 "보도"(3)가 관련 있다는 사실이 숫자에서 드러나지 않습니다.

3.2 의미를 가진 벡터 — Word2Vec의 발상

2013년 구글의 Word2Vec은 혁명적 발상을 선보였습니다. *"비슷한 맥락에 등장하는 단어들은 비슷한 의미를 가진다"*는 분포 가설(distributional hypothesis)에 기반해, 단어를 한 차원의 숫자가 아닌 수백 차원의 벡터로 표현했습니다.

"기자"      → [0.21, -0.43, 0.88, ..., 0.15]   (300차원)
"기자들"    → [0.20, -0.41, 0.85, ..., 0.16]   (거의 같은 방향)
"보도"      → [0.18, -0.39, 0.82, ..., 0.11]   (가까운 방향)
"커피"      → [0.91, 0.55, -0.12, ..., -0.78]  (전혀 다른 방향)

이 벡터들 사이의 방향과 거리가 의미 관계를 담게 됩니다. 가장 유명한 예는 "왕 - 남자 + 여자 ≈ 여왕" 이라는 벡터 연산입니다.

3.3 단어에서 문장으로 — SBERT의 등장

Word2Vec은 단어 단위 임베딩이었습니다. 그러나 우리가 검색하고 싶은 것은 문장과 문단입니다.

단순한 방법은 문장 안 모든 단어 벡터의 평균을 내는 것이었지만, 이 방식은 어순과 문법 구조를 무시합니다. "기자가 정치인을 비판했다"와 "정치인이 기자를 비판했다"가 같은 벡터가 됩니다.

2019년 SBERT(Sentence-BERT)가 이 문제를 풀었습니다. BERT 같은 트랜스포머 모델을 두 문장 짝(pair)으로 미세 조정(fine-tune)해, 문장 전체를 의미 있는 단일 벡터로 만들 수 있게 했습니다. 이후 모든 현대 임베딩 모델은 이 계보를 잇고 있습니다.

3.4 코사인 유사도 — 두 벡터가 얼마나 의미상 비슷한지 측정

두 벡터 a, b의 코사인 유사도는 다음과 같이 계산합니다.

cosine_similarity(a, b) = (a · b) / (||a|| × ||b||)

값의 범위는 -1에서 1입니다. 1에 가까우면 거의 같은 방향(매우 유사), 0이면 무관, -1이면 정반대 의미입니다.

왜 단순 거리(유클리드 거리)가 아닌 코사인을 쓰는가? 코사인은 방향만 보고 크기는 무시합니다. 텍스트 임베딩에서는 벡터의 크기가 문장의 길이나 빈도 같은 비본질적 요인에 영향받을 수 있어, 방향만 비교하는 코사인이 더 안정적입니다.

4장. 임베딩 모델 선택

4.1 이 수업의 표준: Gemini Embedding

이 수업에서는 gemini-embedding-001 을 사용합니다. 선택 이유는 다음과 같습니다.

  • GPU 불필요. API 호출 방식이라 학생 노트북에 모델을 다운로드할 필요가 없습니다.
  • 한국어 강함. 다국어 임베딩 리더보드(MTEB Multilingual)에서 상위권이며, 한국어 텍스트에 안정적입니다.
  • 무료 tier 충분. AI Studio에서 카드 없이 키 발급, 임베딩 호출 한도가 학생 실습 규모에는 사실상 무제한입니다.
  • 차원 선택 가능. 기본 3,072차원이지만 Matryoshka 기법으로 768·1536차원으로 잘라 쓸 수 있어 저장 비용이 줄어듭니다.
import google.generativeai as genai
genai.configure(api_key="YOUR_KEY")

result = genai.embed_content(
    model="gemini-embedding-001",
    content="언론중재위원회의 정정보도 결정 기준은 무엇인가요?",
    task_type="retrieval_query",       # 검색 쿼리용 임베딩
    output_dimensionality=768          # 768차원으로 절단
)
embedding = result["embedding"]        # 길이 768의 리스트

4.1.1 task_type — 비대칭 임베딩의 핵심

Gemini Embedding은 비대칭 임베딩(asymmetric embedding) 을 지원합니다. 문서를 DB에 저장할 때와 사용자 질문으로 검색할 때는 임베딩을 약간 다른 방식으로 조정하는 것이 검색 정확도를 높입니다.

이유는 직관적입니다. 저장되는 문서는 보통 서술문입니다 — 예: "방송심의위원회 위원의 임기는 3년으로 한다." 반면 질문은 의문문입니다 — 예: "방송심의위원회 위원의 임기는?" 두 문장이 의미적으로 같은 답을 가리키지만 표면 구조가 다릅니다. task_type을 명시하면 모델이 "이건 검색 대상 문서" 또는 "이건 검색 쿼리" 라는 신호를 받아 양쪽이 같은 의미 공간에서 더 가깝게 매핑되도록 조정합니다.

Gemini Embedding이 지원하는 task_type 전체 목록은 다음과 같습니다.

task_type 용도
retrieval_document 벡터 DB에 저장할 문서 임베딩 (RAG 빌드 시)
retrieval_query 검색 쿼리 임베딩 (RAG 사용자 질문)
question_answering QA 데이터셋의 질문-문서 매칭용 임베딩
fact_verification 사실 검증용 (fact-check 시스템의 주장 임베딩)
semantic_similarity 두 문장의 의미 유사도 비교 (대칭 임베딩)
classification 분류 모델의 입력 임베딩
clustering 군집화용 임베딩
code_retrieval_query 코드 검색 쿼리 임베딩

핵심 원칙: 같은 코퍼스에 대해 빌드 때와 쿼리 때는 반드시 짝을 맞춰야 합니다.

  • 일반 RAG: 빌드 retrieval_document ↔ 쿼리 retrieval_query
  • Fact-check 시스템: 빌드 retrieval_document ↔ 쿼리 fact_verification
  • 두 문서 비교(중복 검출 등): 양쪽 모두 semantic_similarity

짝이 안 맞으면 검색 정확도가 눈에 띄게 떨어집니다. 본 강의의 모든 실습 코드는 이 짝을 맞춰 작성되어 있습니다.

# 빌드 시 — 문서 저장용
doc_emb = genai.embed_content(
    model="gemini-embedding-001",
    content="방송심의위원회 위원의 임기는 3년으로 한다.",
    task_type="retrieval_document",
    output_dimensionality=768
)["embedding"]

# 검색 시 — 사용자 질문용
query_emb = genai.embed_content(
    model="gemini-embedding-001",
    content="방송심의위원회 위원의 임기는?",
    task_type="retrieval_query",
    output_dimensionality=768
)["embedding"]

4.2 한국어 SBERT 계열 — 오픈소스 대안

학생들이 "모델 자체가 어떻게 생겼는지" 를 보고 싶거나, 인터넷 없이 오프라인으로 돌리고 싶거나, Gemini가 닿지 않는 미래 시점을 대비하려면 한국어 SBERT 모델을 함께 알아두는 것이 좋습니다.

CPU만으로 추론 가능한 대표적 한국어 모델은 다음과 같습니다.

모델 차원 크기 특징
jhgan/ko-sroberta-multitask 768 약 430MB 가장 널리 쓰이는 한국어 SBERT
BM-K/KoSimCSE-roberta 768 약 430MB SimCSE 기법으로 정밀도 향상
snunlp/KR-SBERT-V40K-klueNLI-augSTS 768 약 430MB KLUE 데이터셋 학습, 서울대 NLP

CPU에서 한 문장 임베딩에 약 50~200ms 정도 걸리므로, 수백 개 문서 처리에는 충분합니다. 수만 개 처리는 시간이 오래 걸리니 Gemini API가 낫습니다.

5장. 청킹 — RAG의 숨은 핵심

5.1 청킹이 왜 필요한가

긴 문서를 통째로 임베딩하면 두 가지 문제가 생깁니다.

의미가 평균화된다. 방송법 전체를 하나의 벡터로 만들면, 그 벡터는 "방송법 전반"이라는 모호한 의미만 가집니다. 학생이 *"심의위원 임기"*에 대해 물었을 때, 이 거대한 벡터는 "심의위원 임기" 임베딩과 적당히 유사하긴 하지만 특별히 유사하지는 않습니다.

LLM 컨텍스트를 낭비한다. 검색된 문서를 LLM에 통째로 넘기면 무료 LLM의 컨텍스트 한도를 금세 채웁니다. 정작 답변에 필요한 부분은 그 안의 한 문단뿐일 수 있는데도 말입니다.

해결책은 문서를 적절한 크기의 청크로 잘라 각 청크를 따로 임베딩하는 것입니다. 그러면 "심의위원 임기" 질문에는 해당 조항을 담은 청크가 정확히 매칭됩니다.

5.2 청킹 전략의 다섯 가지 유형

(1) 고정 길이 청킹 (Fixed-size chunking)

가장 단순한 방법입니다. 글자 수나 토큰 수 기준으로 일정 길이마다 자릅니다. 예: 500자마다.

def fixed_chunk(text, chunk_size=500):
    return [text[i:i+chunk_size] for i in range(0, len(text), chunk_size)]

장점: 구현이 가장 단순. 단점: 문장이나 단락 중간에서 잘릴 수 있어 의미가 잘립니다.

(2) 슬라이딩 윈도우 (오버랩 포함)

청크가 의미 단위 중간에서 잘리는 문제를 완화하기 위해, 인접 청크가 일정 부분 겹치게 자릅니다. 예: 500자 청크, 100자 오버랩.

def sliding_chunk(text, chunk_size=500, overlap=100):
    chunks = []
    start = 0
    while start < len(text):
        chunks.append(text[start:start+chunk_size])
        start += chunk_size - overlap
    return chunks

오버랩 덕분에 청크 경계에 걸친 문장도 적어도 한 청크에는 온전히 포함됩니다.

(3) 재귀적 청킹 (Recursive chunking)

가장 실용적인 방법입니다. 문서를 큰 단위(단락 → 문장 → 단어) 순으로 재귀적으로 분할합니다. LangChain의 RecursiveCharacterTextSplitter가 표준 구현입니다.

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", ". ", " ", ""]   # 우선순위: 단락 → 줄바꿈 → 문장 → 어절
)
chunks = splitter.split_text(text)

원리: 먼저 단락(\n\n) 단위로 자르고, 청크가 너무 크면 줄바꿈으로 다시 자르고, 그래도 크면 문장으로, 그래도 크면 어절로 자릅니다. 의미 단위를 가능한 한 보존하는 분할 방식입니다.

(4) 의미 기반 청킹 (Semantic chunking)

문장 단위로 임베딩한 뒤, 연속한 문장의 임베딩 유사도가 갑자기 떨어지는 지점을 청크 경계로 삼습니다. 주제가 바뀌는 곳에서 자연스럽게 잘리지만, 임베딩 호출이 많아져 빌드 비용이 높습니다.

(5) 구조 기반 청킹

문서가 명확한 구조를 가질 때 그 구조를 따릅니다. 예시:

  • 법령: 조(條) 단위로 분할 (제1조, 제2조, ...)
  • 회의록: 발언 단위로 분할 (○○○ 의원: ...)
  • 판결문: 주문 / 이유 / 청구취지 단위로 분할
  • 마크다운: #, ## 헤더 단위로 분할

도메인 특성을 살린 가장 강력한 청킹 방식입니다.

5.3 청크 크기와 오버랩, 어떻게 정하나

경험적 권장값 (한국어 기준):

  • 일반 텍스트: 300~500자, 오버랩 50자
  • 뉴스 기사: 200~400자, 오버랩 30자
  • 법령 조문: 조 단위 (조 자체가 자연스러운 청크)
  • 회의록: 발언 단위 (발언 자체가 자연스러운 청크)
  • 학술 논문: 500~800자, 오버랩 100자

결정 원칙: 답변에 필요한 정보가 한 청크에 온전히 담겨야 한다는 것이 기준입니다. 청크가 너무 작으면 답변에 필요한 맥락이 잘리고, 너무 크면 한 청크에 여러 주제가 섞여 검색 정밀도가 떨어집니다.

5.4 도메인별 청킹 사례

미디어학과 자료별로 권장 청킹 전략을 정리하면 다음과 같습니다.

자료 권장 청킹 이유
언론중재위 결정문 결정문 1건 = 1청크 또는 결정문 내 섹션 단위 한 결정의 맥락이 한 청크에 담겨야 함
방송법 등 법령 조(條) 단위 조 단위 인용이 표준이라 출처 명시에도 유리
국회 회의록 발언 단위 또는 의제별 단위 누가 무엇을 발언했는지가 핵심 정보
뉴스 기사 기사 1편 = 1청크 (단, 짧은 기사만) 기사 분량이 짧으면 통째로, 길면 단락

6장. 벡터 DB

6.1 왜 일반 DB가 아닌가

수만 개 청크 임베딩을 저장한 뒤 "이 질문 벡터와 가장 가까운 청크 5개를 찾아라" 라고 요청하는 상황을 생각해 봅시다. 일반 SQL DB로는 모든 청크와 코사인 유사도를 일일이 계산해야 합니다. 1만 개면 1만 번, 10만 개면 10만 번 계산입니다. 매 질문마다 이러면 너무 느립니다.

벡터 DB는 유사도 검색에 특화된 자료구조(HNSW, IVF 등)를 사용해 이 검색을 수십 밀리초 안에 끝냅니다. 정확도는 근사(approximate)지만 실용적으로 충분합니다.

6.2 이 수업의 표준: Chroma

Chroma는 학습용으로 가장 적합한 벡터 DB입니다.

  • pip 설치 한 번으로 시작
  • 파이썬 API가 직관적
  • 로컬 디스크에 SQLite로 저장 → 학생이 폴더를 USB에 담아 다닐 수 있음
  • LangChain 튜토리얼의 표준
  • 무료, 오픈소스
import chromadb

client = chromadb.PersistentClient(path="./my_chroma_db")
collection = client.get_or_create_collection("news")

collection.add(
    ids=["doc_001"],
    embeddings=[[0.1, 0.2, ..., 0.5]],   # 768차원
    documents=["원본 텍스트"],
    metadatas=[{"source": "한겨레", "date": "2026-01-15"}]
)

results = collection.query(
    query_embeddings=[[0.11, 0.19, ..., 0.48]],
    n_results=5,
    where={"source": "한겨레"}   # 메타데이터 필터링
)

6.3 다른 벡터 DB들 (배포·확장 단계용)

벡터 DB 형태 무료 한도 특징
Chroma 로컬 라이브러리 무제한 (로컬) 학습용 표준

수업에서는 Chroma로 시작하고, 학기 후반에 Vectorize나 Qdrant로 옮기는 흐름이 권장됩니다.

7장. 검색 단계 심화

7.1 단순 top-k 검색

가장 기본은 질문 벡터와 가장 가까운 청크 k개를 반환하는 것입니다. 일반적으로 k=3~10입니다.

results = collection.query(query_embeddings=[q_vec], n_results=5)

7.2 MMR — 다양성과 관련성의 균형

단순 top-k는 거의 같은 내용의 청크 다섯 개가 반환되는 문제가 있습니다. 예를 들어 *"정정보도 청구"*를 검색하면 매우 유사한 결정문 다섯 개가 모두 비슷한 부분을 인용해 답변에 도움이 안 됩니다.

MMR(Maximal Marginal Relevance) 는 관련성과 서로 간 다양성을 함께 고려해 청크를 선택합니다. 첫 번째 청크는 가장 관련성 높은 것을 뽑고, 그 다음부터는 이미 뽑힌 청크와 너무 비슷하지 않으면서 질문과는 충분히 관련된 청크를 뽑습니다.

7.3 메타데이터 필터링

순수 의미 검색만으로는 "2023년에 한겨레가 받은 정정보도 결정" 같은 복합 조건을 처리하기 어렵습니다. 메타데이터를 청크에 함께 저장하면 SQL 조건처럼 필터링할 수 있습니다.

results = collection.query(
    query_embeddings=[q_vec],
    n_results=5,
    where={
        "$and": [
            {"source": {"$eq": "한겨레"}},
            {"year": {"$eq": 2023}}
        ]
    }
)

7.4 하이브리드 검색 (BM25 + 임베딩)

의미 검색은 *"기자 폭행"*을 *"언론인 가해"*와도 매칭시키는 강점이 있지만, 고유명사·정확한 어구에는 약합니다. *"방송법 제33조"*를 정확히 찾고 싶을 때는 키워드 검색(BM25)이 더 정확합니다. 최근에는 사용자의 자연어 질문을 그대로 검색하지 않고, LLM이 먼저 핵심 키워드나 검색 질의(query)를 재구성한 뒤 BM25 검색을 수행하는 방식도 널리 활용된다. 예를 들어 *“기자가 폭행당한 사건 관련 법률”*이라는 질문을 LLM이 “기자 폭행”, “언론인 폭행”, “관련 법 조항” 등의 검색어로 정제한 뒤 검색하는 방식이다. 하이브리드 검색은 이러한 키워드 기반 검색(BM25)과 임베딩 기반 의미 검색을 함께 결합하는 접근이다. 즉, 정확한 어구 검색의 강점과 의미적 유사성 검색의 장점을 동시에 활용하는 방식이다.

7.5 리랭킹 (Re-ranking)

검색된 청크들을 별도의 정밀한 모델로 다시 정렬하는 단계입니다. 임베딩 검색은 빠르지만 거칠고, 리랭커는 느리지만 정밀합니다. 임베딩으로 100개 후보를 뽑고 리랭커가 5개로 추리는 패턴이 표준입니다. 무료 옵션으로 BAAI/bge-reranker-v2-m3가 있습니다.

9장. 평가

9.1 무엇을 평가하나

RAG 평가는 세 측면으로 나뉩니다.

  1. 검색 품질 (Retrieval quality): 검색기가 정답을 포함한 청크를 가져왔는가?
  2. 답변 충실도 (Faithfulness): 답변이 검색된 청크에 근거하는가? 청크에 없는 주장이 들어가지 않았는가?
  3. 답변 관련성 (Answer relevance): 답변이 질문에 실제로 답하는가?

9.2 간단한 평가 셋 만들기

학기 프로젝트 수준에서는 30~50건의 "질문 ↔ 정답 청크 ↔ 모범 답안" 쌍을 직접 만들어 평가하는 것이 현실적입니다.

eval_set = [
    {
        "question": "언론중재위원회 결정에 불복할 경우 절차는?",
        "expected_chunk_id": "doc_045",
        "expected_answer_keywords": ["행정소송", "60일", "관할법원"]
    },
    # ... 30개 이상
]

검색이 expected_chunk를 top-5 안에 포함하면 검색 성공으로 카운트, 답변이 expected_keywords를 모두 포함하면 답변 성공으로 카운트합니다.

본격적 평가는 RAGAS, TruLens 같은 도구가 있지만 학부 수업 범위는 넘어섭니다.

10.3 빌드 파이프라인 — 청킹부터 저장까지

# build_index.py
import os
import glob
import time
import chromadb
import google.generativeai as genai
from langchain.text_splitter import RecursiveCharacterTextSplitter

# 1) Gemini 설정
genai.configure(api_key=os.environ["GEMINI_API_KEY"])

# 2) Chroma 클라이언트 생성 (로컬 디스크에 저장)
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection(
    name="media_law",
    metadata={"hnsw:space": "cosine"}   # 코사인 유사도 사용
)

# 3) 청킹 도구 준비
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", "。 ", ". ", " ", ""]
)

# 4) 모든 텍스트 파일 처리
files = glob.glob("./data/**/*.txt", recursive=True)
print(f"총 {len(files)}개 파일 처리 시작")

doc_id = 0
for filepath in files:
    with open(filepath, "r", encoding="utf-8") as f:
        text = f.read()
    
    # 파일 정보를 메타데이터에 저장
    filename = os.path.basename(filepath)
    category = "법령" if "법" in filename else "결정문"
    
    # 청킹
    chunks = splitter.split_text(text)
    print(f"  {filename}: {len(chunks)}개 청크")
    
    # 청크별로 임베딩 + 저장
    for chunk_idx, chunk in enumerate(chunks):
        # Gemini 임베딩 호출 (저장용: retrieval_document)
        result = genai.embed_content(
            model="gemini-embedding-001",
            content=chunk,
            task_type="retrieval_document",
            output_dimensionality=768
        )
        embedding = result["embedding"]
        
        # Chroma에 추가
        collection.add(
            ids=[f"doc_{doc_id:05d}"],
            embeddings=[embedding],
            documents=[chunk],
            metadatas=[{
                "source": filename,
                "category": category,
                "chunk_idx": chunk_idx
            }]
        )
        doc_id += 1
        
        # rate limit 회피
        time.sleep(0.1)

print(f"\n총 {doc_id}개 청크가 ./chroma_db 에 저장되었습니다.")

이 스크립트를 한 번 실행하면 ./chroma_db/ 폴더에 모든 청크의 임베딩이 저장됩니다. 이후로는 이 폴더만 있으면 즉시 검색이 가능합니다.

10.4 쿼리 파이프라인 — 질문에서 답변까지

# query.py
import os
import chromadb
import google.generativeai as genai

genai.configure(api_key=os.environ["GEMINI_API_KEY"])

client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_collection("media_law")

def search(query, top_k=5):
    """질문에 가장 관련 있는 청크 top_k개 검색"""
    q_emb = genai.embed_content(
        model="gemini-embedding-001",
        content=query,
        task_type="retrieval_query",
        output_dimensionality=768
    )["embedding"]
    
    results = collection.query(
        query_embeddings=[q_emb],
        n_results=top_k,
        include=["documents", "metadatas", "distances"]
    )
    return results

def answer(query):
    """검색 + 생성 통합 함수"""
    # 1) 관련 청크 검색
    results = search(query, top_k=5)
    chunks = results["documents"][0]
    metas = results["metadatas"][0]
    
    # 2) 검색 결과로 컨텍스트 구성
    context = ""
    for i, (chunk, meta) in enumerate(zip(chunks, metas)):
        context += f"\n[문서 {i+1}] (출처: {meta['source']})\n{chunk}\n"
    
    # 3) LLM에 질문 + 컨텍스트 전달
    prompt = f"""다음 문서들을 참고하여 질문에 답하세요.

규칙:

1. 답변의 각 주장 끝에 [문서 N] 형식으로 출처를 표기하세요.
2. 주어진 문서에 없는 내용은 추측하지 말고 "제공된 자료로는 답할 수 없습니다"라고 답하세요.
3. 답변은 한국어로 작성하세요.

{context}

질문: {query}

답변:"""
    
    model = genai.GenerativeModel("gemini-2.5-flash")
    response = model.generate_content(prompt)
    return response.text, metas

# 테스트
if __name__ == "__main__":
    question = "방송심의위원회 위원의 임기는 얼마인가요?"
    answer_text, sources = answer(question)
    print("질문:", question)
    print("\n답변:\n", answer_text)
    print("\n참고 출처:", [m["source"] for m in sources])

# app.py
import os
import chromadb
import gradio as gr
import google.generativeai as genai

genai.configure(api_key=os.environ["GEMINI_API_KEY"])
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_collection("media_law")

def rag_chat(message, history):
    # 검색 (쿼리용 임베딩)
    q_emb = genai.embed_content(
        model="gemini-embedding-001",
        content=message,
        task_type="retrieval_query",
        output_dimensionality=768
    )["embedding"]
    results = collection.query(query_embeddings=[q_emb], n_results=5,
                                include=["documents", "metadatas"])
    chunks = results["documents"][0]
    metas = results["metadatas"][0]
    
    # 컨텍스트
    context = "\n\n".join(
        f"[문서 {i+1}] (출처: {m['source']})\n{c}"

    )
    
    # 답변 생성

질문: {message}
답변:"""

10.6 자주 만나는 오류와 해결

오류 1: RESOURCE_EXHAUSTED 또는 quota exceeded

  • 원인: Gemini 무료 tier 일일 호출 한도 초과
  • 해결: 다음 날 재시도 또는 time.sleep()을 늘려 호출 간격 조절

오류 2: Embedding dimension mismatch

  • 원인: 빌드 때 768차원으로 만들고 쿼리 때는 3,072차원으로 호출
  • 해결: 모든 호출에 output_dimensionality=768을 명시

오류 3: 검색 결과가 엉뚱함

  • 원인: 청크 크기가 너무 큼 (의미가 평균화) 또는 너무 작음 (맥락 부족)
  • 해결: 청크 크기를 300~800자 범위에서 조절하며 실험

오류 4: 답변이 자료에 없는 내용을 포함

  • 원인: 프롬프트에서 "모른다고 답하라"는 지시가 약함
  • 해결: 프롬프트 첫 줄에 강한 제약 추가, temperature=0.1 설정

11장. RAG의 한계 — 단순 RAG가 못 푸는 것들

지금까지 만든 RAG는 단순 의미 검색 기반 RAG입니다. 강력하지만 다음 문제들에는 약합니다.

11.1 다단계 추론 (Multi-hop reasoning)

"2023년 정정보도 결정을 가장 많이 받은 신문사의 모회사는 어디인가?"

이 질문은 두 단계 추론을 요구합니다. (1) 결정문에서 신문사별 빈도 세기 → (2) 신문사 모회사 정보를 또 다른 자료에서 찾기. 단순 의미 검색은 이런 연결을 잡지 못합니다.

11.2 집계 질문

"이번 해 한겨레가 받은 정정보도 결정은 총 몇 건인가?"

이건 의미 검색이 아니라 카운팅이 필요합니다. SQL이 잘하는 일이고 임베딩이 못하는 일입니다.

11.3 정보 단편화

긴 보고서에서 한 결론이 여러 단락에 흩어져 있을 때, 단편 청크 몇 개로는 전체 맥락을 복원하기 어렵습니다.

11.4 정확한 인용

*"방송법 제33조 제2항"*을 정확히 검색하고 싶을 때 의미 검색은 비슷한 의미의 조항을 가져올 수 있습니다. 키워드 검색 결합(하이브리드)이 필요합니다.

12장. RAG의 발전 방향 — GraphRAG와 그 너머

12.1 GraphRAG의 핵심 아이디어

GraphRAG는 마이크로소프트 리서치가 2024년 제안한 방식으로, 문서들을 단순 청크가 아니라 지식 그래프로 표현하는 접근입니다.

핵심 아이디어: 문서에서 엔티티(인물·조직·사건)와 관계(누가 누구를 비판했다, 어디서 일어났다)를 LLM으로 추출해 그래프로 만듭니다. 그래프에서 공동체(community)를 자동 탐지하고 각 공동체에 대한 요약을 미리 생성해 둡니다. 질문이 들어오면 관련 공동체의 요약을 함께 LLM에 전달합니다.

일반 RAG: 문서 → 청크 → 임베딩 → 유사도 검색
GraphRAG: 문서 → 엔티티·관계 추출 → 그래프 → 공동체 탐지 → 요약 → 검색

왜 강한가: 단편 청크는 연결을 잃어버리지만, 그래프는 연결을 보존합니다. "누가 누구를 어떻게 비판했는가" 같은 관계 질문에 강합니다.

12.2 한국어 미디어 사례

GraphRAG는 본 강의의 교수 연구실에서도 활용되고 있습니다. 1979~1981년 한국 군부 검열 기록을 언론사·기자·검열관·기사 주제 노드와 검열·발표 금지·삭제 요구 관계로 그래프화한 사례가 있습니다(약 10,500 노드, 86,000 관계). 일반 RAG로는 "○○일보 검열을 가장 많이 지시한 검열관" 같은 관계 질문에 답하기 어렵지만, GraphRAG는 자연스럽게 답합니다.

12.3 Agentic RAG

LLM이 어떻게 검색할지를 스스로 계획하는 방식입니다. 다단계 추론 질문이 들어오면 LLM이 검색→평가→재검색→집계의 단계를 자동으로 수행합니다. LangGraph 같은 프레임워크가 이를 지원합니다.

12.4 Multi-vector Retrieval

한 문서를 한 벡터가 아니라 여러 벡터(요약, 가설 질문, 원본 등)로 표현해 검색하는 방식입니다. ColBERT, ColPali 같은 모델이 이 방향을 발전시키고 있습니다.

12.5 더 공부하고 싶다면

  • 이론: Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" (NeurIPS 2020) — RAG 원논문
  • GraphRAG: Edge et al., "From Local to Global: A Graph RAG Approach" (2024)
  • 실습: LangChain·LlamaIndex 공식 튜토리얼
  • 평가: Es et al., "RAGAS: Automated Evaluation of Retrieval Augmented Generation" (2023)

부록 B. 트러블슈팅 체크리스트

증상 가능한 원인 점검 사항
검색 결과가 항상 같은 청크만 코퍼스가 너무 작음 또는 모두 비슷한 내용 청크 수 확인, 도메인 다양성 확인
답변이 자료와 무관한 내용 LLM 환각, 프롬프트 약함 "자료에 없으면 모른다고 답하라" 강조, temperature 낮춤
한국어 임베딩 성능 낮음 영어 위주 모델 사용 Gemini Embedding이나 한국어 SBERT로 교체
검색 정확도가 미묘하게 떨어짐 빌드와 쿼리의 task_type 불일치 빌드 retrieval_document ↔ 쿼리 retrieval_query 짝 맞춤
빌드가 너무 느림 청크가 너무 많음, rate limit batch 호출, time.sleep 조절
같은 질문이 매번 다른 답 LLM 무작위성 temperature=0.1 설정
검색은 잘 되는데 답변이 짧음 LLM 출력 제한 max_output_tokens 늘림
메타데이터 필터링 안 됨 필드명 오타, 타입 불일치 metadata 키와 where 절 일치 확인

마무리하며

RAG는 기술이지만 그 본질은 정직함입니다. *"내가 모르는 것은 모른다고 인정하고, 답하기 전에 자료를 찾아본다"*는 태도를, LLM에게 시스템 차원에서 강제하는 방법입니다. 미디어학과 학생에게 이 태도는 특히 중요합니다. 저널리즘의 기본 윤리 — 출처 확인, 사실 확인 — 와 정확히 일치하기 때문입니다.

이 강의를 마친 학생이 *"AI가 만든 답이지만 출처가 명시되어 있어 확인할 수 있다"*는 시스템을 직접 만들 수 있게 되었다면, 강의의 목표는 달성된 것입니다. 더 정교한 기술은 그 다음입니다.

좋은 RAG는 완벽한 답이 아니라 근거 있는 답을 만드는 시스템입니다. 그 차이를 이해하는 것이 이 강의 전체의 핵심입니다.
